When you generate a project from a template, Toha can remember what it wrote so
that a later version of the template updates the project without overwriting the
edits you made in between. It does this with a **snapshot**: the stored output of
one apply, kept as a git commit under a Toha-owned ref.

## Record a snapshot

Apply a template into a git repository that has a commit and no uncommitted
changes:

```sh
toha apply ./note-template ./project --answers answers.json
```

The `applied` result document's `snapshot` member names the snapshot it saved.
If the target is not a git repository, has no commit, was dirty, or the apply
changed nothing, the apply still writes its files and `snapshot` names why it
saved none — for example `{"skipped": "dirty"}`.

List a project's snapshots, newest first:

```sh
toha snapshots list ./project
```

## Update from a snapshot

Later, point `apply --from` at a snapshot to carry the template's changes into
the project:

```sh
toha apply ./note-template ./project --from 01J9Z8...
```

Toha re-renders the template, replays the answers the snapshot recorded, asks
only a question the new version added, and merges the difference three-way from
the snapshot. Your own edits to the generated files survive; where the template
and your edits touched the same lines, Toha writes the file with conflict markers
and leaves it for you to resolve. Human and completed staged-agent updates print
the template and target, each merge action or conflict, messages, and the saved
snapshot id. A preview says no changes were written; an unchanged render says
`Already current.`. Conflicts include instructions to resolve them before
committing. With `--answers`, the scripted route returns an `applied` document
with a `merge` member, or `already-current` when the render matches the snapshot.

Update interactively, and Toha prompts anything the recorded answers do not
settle. An agent stages the update instead:

```sh
toha stage ./note-template ./project --from 01J9Z8... --async
toha continue ./project answers.json
toha apply ./project
```

## Adopt an existing project

If a project was not generated by Toha, or has no snapshot yet, `--baseline`
adopts it: Toha merges the whole render against an empty base, so your existing
files survive, and records the first snapshot.

```sh
toha apply ./note-template ./project --baseline --answers answers.json
```

## A worked example

Start with a template that renders one file from one answer:

`note-template/template.yml`

```yaml
name: note
interview:
  - id: title
    type: text
    prompt: Title
    required: true
```

`note-template/template/note.md`

```text
# {{ title }}
```

Create `answers.json` with the template's canonical absolute folder path. For
example, if the template is at `/tmp/note-template`:

```json
{
  "template": "/tmp/note-template",
  "answers": { "title": "Sample note" }
}
```

Use your template's actual path. An agent batch exposes this identity in
`context.template`; copy that value exactly into each external answers document.

Apply it and commit the result:

```sh
toha apply ./note-template ./project --answers answers.json
git -C ./project add . && git -C ./project commit -m "generate note"
```

Now the template grows a second question and a new file:

`note-template/template.yml`

```yaml
name: note
interview:
  - id: title
    type: text
    prompt: Title
    required: true
  - id: status
    type: text
    prompt: Status
    required: true
```

`note-template/template/status.md`

```text
Status: {{ status }}
```

Update the project from its snapshot, answering only the new question:

```sh
toha apply ./note-template ./project --from <snapshot-id>
```

Toha keeps `note.md` as the snapshot answered it, adds `status.md` with your new
answer, and — because you committed your own change to `note.md` first — merges
that change through untouched.
