# Confined Jinja includes — candidate 2

**Distinctive spine.** Includes are turned on by a *type*, not a flag. One value
object, `Partials`, owns the single confined loader and is built from
`template.root`. It compiles a file body into a distinct `FileTmpl` that carries
that loader. Only the two file-body call sites in `plan.rs` construct a
`FileTmpl`; every other render surface keeps the existing loaderless `Tmpl`, so
`{% include %}` cannot be enabled anywhere else by accident. Include names are
**root-relative** (fixed root = `template.root`); partials live outside the
source subdirectory and are therefore never emitted.

---

## 1. Caller's view (template author)

### Quickstart

Put shared fragments in support material — anywhere under the template root
*outside* the source subdirectory — and pull them into a file body with
`{% include "path/relative/to/template/root" %}`. Names are always relative to
the template root, never to the including file. Partials see the same variables
(answers, `data`, computed values) as the file that includes them.

```
my-template/
├── template.yml            # source: template   (the default)
├── partials/               # support material — NEVER emitted
│   ├── header.md
│   └── footer.md
└── template/               # the source subdirectory — emitted
    └── README.md           # includes the partials
```

`import` and `extends` stay unavailable. The YAML `!include` tag in
`template.yml` is a separate feature and keeps its own diagnostics.

### Call site A — a source file pulls in a shared header

`partials/header.md`

```jinja
<!-- {{ project | title }} — generated by Toha, do not edit by hand -->
```

`template/README.md`

```jinja
{% include "partials/header.md" %}
# {{ project | title }}

{{ summary }}
```

With `project = "acme widgets"`, `summary = "A tiny CLI."`, the emitted
`README.md` becomes:

```markdown
<!-- Acme Widgets — generated by Toha, do not edit by hand -->
# Acme Widgets

A tiny CLI.
```

Only `template/README.md` is written. `partials/header.md` is support material
outside the source subdirectory, so it is never walked and never emitted — no
`ignore` entry needed.

### Call site B — nested includes (a partial includes a partial)

`partials/badges.md`

```jinja
{% include "partials/license.md" %}
![build](https://img.example/build.svg)
```

`partials/license.md`

```jinja
![license: {{ license }}](https://img.example/{{ license | lower }}.svg)
```

`template/README.md`

```jinja
{% include "partials/badges.md" %}
```

Nesting works because every name is resolved from the template root, so a
partial names the partial it wants by the same root-relative path any file
would use. With `license = "MIT"` the output is the license badge line followed
by the build badge line.

### Call site C — a `files:` rule source uses a partial

```yaml
# template.yml (excerpt)
files:
  - each: services
    source: partials/service.yml       # confined_file path, as today
    path: "deploy/{{ item.name | kebab }}.yml"
```

`partials/service.yml`

```jinja
name: {{ item.name }}
{% include "partials/service-defaults.yml" %}
```

Each rendered rule file may `{% include %}` the same way a source-tree file can.
These are the **only two** surfaces that gain includes (see §5).

### What an author does *not* get

- `{% include %}` in a prompt, default, `when`, `computed`, `format`, options,
  an apply message, a hook field, or a **target path segment** does not resolve
  a partial — it behaves exactly as today (the name is not found). Partials
  factor *file bodies*, not question text or filenames.
- Absolute names, `..` escapes, and symlinked partials are refused (§4).

## 2. Data / type sketch

The public surface is three items. Everything about confinement lives behind
them.

```rust
// src/jinja.rs

/// The include boundary for one loaded template. Built once from the canonical
/// template root; cloned into every file-body render. Owns the ONLY loader that
/// a Jinja `{% include %}` can reach, so it is the single confinement seam.
///
/// Invariant: `root` is already canonical (it is `Template::root`, which
/// `Template::load` canonicalizes). Names are resolved relative to `root`.
#[derive(Clone, Debug)]
pub struct Partials {
    root: std::sync::Arc<std::path::PathBuf>,
}

/// A compiled file body that MAY resolve `{% include %}` against its `Partials`.
/// A distinct type from `Tmpl`: possessing one is the capability. It is never
/// stored, only compiled-then-rendered inside `plan.rs` file-body call sites.
pub struct FileTmpl {
    source: String,
    env: minijinja::Environment<'static>, // loader already attached
    referenced_ids: std::collections::HashSet<String>,
}
```

`Tmpl` and `Expr` are unchanged. `Tmpl` stays the loaderless template used by
every non-file surface; `{% include %}` inside a `Tmpl` still fails to resolve,
exactly as today. This is the invariant encoded in the type split
(per `encode-lessons-in-structure`): includes are reachable **iff** you hold a
`FileTmpl`, and only `Partials::compile` mints one.

### Dominant access patterns traced

- *Render a source-tree file* → `Partials::compile(text)?.render(ctx)`. The env
  already holds the confined loader; render consults it verbatim per include.
- *Render a `files:` rule source* → same call, same `Partials`.
- *Resolve one partial name* → loader closure: `root.join(name)` →
  per-component symlink refusal → canonicalize → `starts_with(root)` → read.
  No index or cache is added; MiniJinja caches compiled partials by name within
  the env for the life of one `FileTmpl`, which is exactly one file render.
- *Detect a cycle* → MiniJinja's recursion limit fires; `FileTmpl::render`
  translates that one error kind into the partial-cycle diagnostic.

No "we'll add a map later" gap: the flat global answer namespace means every
partial sees the same context regardless of includer, so no per-includer
binding table is ever needed.

## 4. Error / results contract (every diagnostic string)

All Jinja-include diagnostics contain the word **partial** so they never collide
with the YAML `!include` set (`include escapes template root`, `include cycle`,
`include file not found`, `unsupported include extension`). The including file
is named by the existing `PlanError::Render { path, .. }` wrapper; the partial
name is named by the message.

| Situation | Message (from the loader / `FileTmpl`) | Wrapped as |
| --- | --- | --- |
| Partial name resolves to nothing under root | `included partial not found: {name}` | `PlanError::Render { path=includer, message }` |
| Absolute name, or canonical path escapes root | `include partial escapes template root: {name}` | same |
| A component of the name is a symlink | `include partial crosses a symlink: {name}` | same |
| Partial exists but cannot be read | `include partial cannot be read: {name}` | same |
| Include recursion / cycle (translated) | `include partial recursion limit reached; check for a partial include cycle` | same |
| Undefined id reached only through a partial | MiniJinja's own undefined/`InvalidOperation` render error, prefixed by the including file path | same (render-time; §6) |

Success result is unchanged: `Content::Rendered(String)` for both file-body
surfaces. No new result variant, no new public error type — include failures ride
the existing `PlanError::Render`.

**Non-file surfaces** are unchanged: `{% include %}` there compiles fine (as it
does today) and fails at render with MiniJinja's own `tried to include
non-existing template` — Toha adds no partial resolution for them. That is the
observable proof the seam holds.

## 5. Module / seam map

```
Template::load ── canonicalizes ──▶ template.root  (single source of truth)
                                          │
plan.rs Plan::build ──────────────────────┤ Partials::rooted(&template.root)
   │                                       ▼
   ├─ walk() ─ source-tree file ─▶ read_render(path, ctx, &partials)
   │                                       │
   ├─ files: rule source ────────▶ read_render(origin, ctx, &partials)
   │                                       │
   │                          Partials::compile(text) ─▶ FileTmpl
   │                                       │                 │ render(ctx)
   │                                       │                 ▼
   │                       jinja::environment()  +  set_loader(confined_loader(root))
   │                                                         │
   │                                          ┌──────────────┴───────────────┐
   │                                          │  confined_loader closure       │  ◀── the ONE seam
   │                                          │  absolute? symlink? canon?     │
   │                                          │  starts_with(root)? read       │
   │                                          └────────────────────────────────┘
   │
   ├─ target_path()  ─▶ rendered() ─▶ Tmpl (loaderless)   includes inert
   ├─ messages       ─▶ stored Tmpl (loaderless)          includes inert
   └─ hooks          ─▶ render_hooks ─▶ Tmpl (loaderless) includes inert

interview.rs (pure engine) ─▶ Tmpl / Expr (loaderless)    includes inert, FS-free
template.rs !include resolve() ─▶ SEPARATE, load-time, own diagnostics (untouched)
```

Interface depth: the public surface is `Partials::rooted`, `Partials::compile`,
and `FileTmpl::{render, references, source}`. Behind it sit canonicalization,
three escape-vector checks, the MiniJinja loader wiring, and the recursion→cycle
translation. No wire or MiniJinja loader type is exposed; callers pass a
`&Path` in and get domain results out (per `boundary-discipline`). The whole
feature is reachable and testable through `Plan::build` and the fixture harness.

## 6. The six required decisions

1. **Supported render surfaces — file bodies only.** Source-tree file contents
   *and* `files:` rule sources gain includes; both are the same `read_render`
   path and both render whole file bodies where factoring shared fragments is
   the actual need. One rule: *includes render where file bodies render.*
   Excluded, each with reason: **target path segments** (a segment is a filename
   fragment; injecting multi-line partial text into a path is nonsensical and a
   path/newline-injection hazard); **interview fields** (prompt/default/
   `when`/`computed`/`format`/options are short interactive values, and the
   interview engine must stay a pure, filesystem-free function of template +
   answers across the headless/staged/crate drivers — attaching a loader there
   would break that); **apply messages** (short notices, not files — keeping
   them out keeps the rule crisp); **hook fields** (feed process execution;
   unaudited injection surface). The exclusion is enforced structurally: those
   sites hold a `Tmpl`, which has no loader, so no per-site opt-out is possible.

2. **Include root & lifetime — the whole template root; partials live outside
   the source subdirectory.** Confinement root = `template.root`, the identity
   `Template::load` already establishes and canonicalizes; `Partials::rooted`
   consumes it and defines no new identity. Choosing `template.root` over
   `source_dir` is what lets a partial live as *support material* outside
   `source_dir`, so `walk()` never visits it and it is never emitted — no
   `ignore` entry required and no foot-gun. A partial placed *inside*
   `source_dir` still renders and would also be emitted unless the author adds
   it to `ignore`; the recommended layout avoids that. `static` files are copied
   byte-for-byte and never rendered, so includes never apply to them (unchanged).

3. **Relative / nested semantics — root-relative (fixed root), verbatim.**
   `{% include "partials/x.md" %}` names a path relative to `template.root`.
   This is deliberately **not** relative-to-includer: MiniJinja looks names up
   verbatim and does not rewrite them, so relative-to-includer would require
   rewriting include targets, which needs AST access Toha does not take. Fixed
   root makes nested includes trivial and unambiguous — a partial names the next
   partial by the same root-relative path any file would use — and keeps the one
   confinement rule identical for every include at every depth.

4. **Missing includes — precise, load-name-in-message.** The loader returns a
   crafted `Err` (`included partial not found: {name}`) rather than `Ok(None)`,
   so authors get Toha's wording, not MiniJinja's `tried to include
   non-existing template`. The including file is named by `PlanError::Render`.

5. **Recursion / cycle — translate, don't statically walk.** A cycle degrades to
   MiniJinja's recursion limit (~50 levels). `FileTmpl::render` catches that one
   error and re-emits `include partial recursion limit reached; check for a
   partial include cycle`, prefixed by the including file. We accept the limit
   rather than build a static include-graph walker because include targets may
   be computed (`{% include some_var %}`), so a static walk would be incomplete
   and would need AST access; the translated message is honest for both literal
   and dynamic cycles. (Alternative in rationale.)

6. **Load-time reference validation — includer validated at load, partial refs at
   render.** `undeclared_variables` does not follow includes, and we do not add a
   graph walk. It is unnecessary here: the render context is one *flat, global*
   namespace (all `data` + all answers + all computed), identical for every file
   render, so a partial that references an undefined id fails deterministically
   on first render regardless of which file includes it — the error names the id
   and the including file. Validating a partial's refs eagerly at load would
   require walking includes (again defeated by dynamic names) for no additional
   safety. Flagged as an open question in the rationale for the human to weigh.
