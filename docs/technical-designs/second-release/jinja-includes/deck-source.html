Toha 0.2.0 · Approved design brief

Jinja {% include %} within the template root

Turn on Jinja includes for rendered file bodies, confined to the selected template root, without granting arbitrary filesystem access and without disturbing the separate YAML !include.

design-only second release implementation-ready approved choices

Task

Let a template author factor shared text into any confined root-relative file and pull it into a rendered file body with Jinja {% include %}. Valid examples include notice.txt, shared/legal/license.inc, and partials/frontmatter.md. Today Jinja include/import/extends are disabled: every string compiles as a lone template named "value" in a fresh MiniJinja environment with no loader.

  • Rendered file bodies only. template.yml and any document loaded through its YAML !include get no Jinja include processing — they are configuration, parsed as data. A file's role (body vs configuration) follows how it is referenced, not its extension: a generated .yml/.yaml body still gets includes.
  • Any path under the root. Root-level and nested targets with any extension are valid. partials/ is an example, with no prefix or directory allowlist.
  • Included content stays inside the selected template root; no arbitrary filesystem access through the loader.
  • Reject absolute paths, .. traversal, and symlink escapes — including a symlink inside the root that resolves outside it.
  • Preserve the YAML !include tag as a separate feature with its own diagnostics.
  • Design only. The paired implementation owns canonical spec/schema/guide/example edits.

Base candidate C2 (capability-by-type) + selected graft of C1 (compile-time confined closure). Full package: docs/technical-designs/second-release/jinja-includes/.

Pre-mortem — the design and implementation failed. Why?

  • Confinement bypass. A symlink inside the root points outside; MiniJinja's safe_join/path_loader does not canonicalize, so it follows the link. Mitigation: a custom seam mirroring !include — canonicalize + starts_with(root) + refuse symlink at any component.
  • Diagnostics collide. A Jinja-include message reuses the YAML !include wording ("include cycle"), confusing two features. Mitigation: every Jinja message says "jinja include".
  • Scope creep onto the interview. A loader attached to interview-field templates breaks the pure, filesystem-free interview engine across the headless/staged/crate drivers. Mitigation: includes reachable only by a distinct type minted at the two file-body call sites.
  • Silent cycles. A cycle degrades to a generic "recursion limit exceeded" after ~50 levels with no offending file. Mitigation: the static closure resolves the graph at compile time and names the cycle path.
  • Unstable dependency churn. The approved mode enables MiniJinja's unstable_machinery (no semver guarantee). Keep literal extraction isolated behind Partials.

Module and seam

One value object owns the single confinement seam; two file-body call sites in plan.rs construct the include-capable template. Everything else stays loaderless, so includes are inert there by construction.

Public interfaces expected

New types in src/jinja.rs beside Tmpl. Tmpl and Expr are unchanged and stay loaderless. Navigate down for each item.

Partials — the include boundary

/// Cheap, cloneable handle to the canonical selected template root
/// (consumes selected-template resolution's ResolvedTemplate.folder identity;
/// defines no new one).
/// The ONE seam every include name passes through.
#[derive(Clone, Debug)]
pub struct Partials { root: std::sync::Arc<std::path::PathBuf> }

impl Partials {
    pub fn rooted(root: &std::path::Path) -> Self;         // does not re-canonicalize
    pub fn compile(&self, source: String, label: &str)
        -> Result<FileTmpl, IncludeError>;                 // label = root-relative path, for diagnostics
}

FileTmpl — the capability

/// A compiled file body that MAY resolve {% include %}. A distinct type from
/// Tmpl: holding one IS the include capability; only Partials::compile mints it.
pub struct FileTmpl { /* source, env, referenced_ids */ }

impl FileTmpl {
    pub fn source(&self) -> &str;
    pub fn references(&self) -> &HashSet<String>;          // incl. include-reached ids
    pub fn render<S: Serialize>(&self, ctx: S) -> Result<String, RenderError>;
}

Call-site delta (plan.rs)

// Plan::build: let partials = Partials::rooted(&template.root);
//   thread &partials into walk() and the files: loop.
fn read_render(path: &Path, ctx: &impl Serialize, partials: &Partials)
    -> Result<String, PlanError>;
// rendered() (path segments) is UNCHANGED — no partials param, includes inert.
// IncludeError folds into PlanError::Render via Display, like minijinja::Error today.

Data structures expected

One error enum. Distinct wording from every YAML !include message. No template.yml schema key is added — partials are ordinary files plus inline {% include %}.

pub enum IncludeError {
    Template(minijinja::Error),                 // syntax error, unchanged wording
    NotFound  { name, by },   // "jinja include not found: {name}, included by {by}"
    Escape    { name, by },   // "jinja include escapes template root: {name}, ..."
    Symlink   { name, by },   // "jinja include path is a symlink: {name}, ..."
    NotUtf8   { name, by },   // "jinja include is not utf-8: {name}, ..."
    Unreadable{ name, source},// "jinja include is not readable: {name}: {io}"
    Cycle     { path },       // "jinja include cycle: a.md -> b.md -> a.md"
    Dynamic   { by },         // "... must be a literal string, ..."
}

The selected static mode adds one private structure: the confined closure (root-relative name → confined UTF-8 source, plus the unioned referenced_ids), built by a static walk with a canonical-path stack — the same shape as template.rs::resolve for !include.

Inertness & separation guards

  • A source file name and an apply message / interview default each containing {% include %} render as today (no partial resolution) — proves the loaderless Tmpl path is untouched.
  • include-config-field-inert: a template.yml string field containing {% include "partials/x.md" %} where the target exists in the root still does not resolve it — MiniJinja's generic TemplateNotFound, never Toha's jinja include wording. Proves configuration is not a render surface.
  • include-yaml-include-field-inert: the same string delivered into a field through a YAML !include-loaded fragment behaves identically — !include composes data, the field stays loaderless.
  • No Jinja-include message equals a YAML !include message; the existing err-include-cycle/err-include-escape fixtures still pass.
  • Sole-kill: add a partials/-only restriction → both include-root-level and include-nested-outside-partials fail by name.
  • Sole-kill: invert starts_with(root), drop the symlink refusal, drop absolute/.. rejection each in turn → the matching negative fixture fails by name (symlink fixture holds an in-root symlink, the exhaustive shape).

Out of scope

  • import, extends; dynamic include targets.
  • Jinja include processing of template.yml and any document loaded through its YAML !include tag — configuration is parsed as data, never rendered.
  • Includes on interview fields, expressions, path segments, hook fields, and apply messages.
  • Any change to YAML !include, static, ignore, or path/target confinement; any extension-based rule on which files may be bodies or partials.
  • Any template.yml schema key. Pure interview logic and all terminal/headless/staged/direct/crate paths are preserved.

Reviewer focus — what the adversary attacks

  • Every escape vector at the one seam: absolute, .., and a symlink inside the root resolving outside it. Try to reach a file outside the root.
  • Surface leakage: can {% include %} resolve a partial from any non-file surface (path segment, interview field, message, hook)? It must not.
  • Configuration boundary: does a {% include %} in a template.yml field — or one delivered through YAML !include — ever resolve a partial? It must not; configuration is data, not a render surface. And conversely, is a generated .yml/.yaml body wrongly denied includes by an extension rule?
  • Diagnostic collision: does any Jinja message read like the YAML !include feature?
  • Reference/cycle claims: is an include-only variable really validated at load? Is the cycle path real, or does it degrade to a recursion limit?
  • Driver purity: does anything attach a loader to the interview engine?

Alternatives explored

CandidateShapeWhy not the base
C1Literal-only compile-time closure, no render loader, template.rootStrongest diagnostics/validation — grafted as the selected resolution mode; needs unstable_machinery
C2Capability-by-type (Partials → FileTmpl), render loaderBase: cleanest structural surface enforcement, no unstable dep
C3source_dir root, relative-to-includer, static graphLeaks includes onto interview fields; forces ignore ceremony
C4template.root, relative-to-includer via RefCell loaderRefCell not Sync (set_loader needs Send+Sync); dead symlink check; cycle wording collides

Both scorers ranked C1 > C2 > C3 > C4. Rejected across the board: relative-to-includer (needs name rewriting MiniJinja does not do) and source_dir confinement (no security gain).

Approved choices

  • Static compile-time closure. Literal targets, named cycle paths, author-time confinement errors, load-time reference validation, and no render-time filesystem access. Enable MiniJinja unstable_machinery for literal extraction.
  • Rendered file bodies only. Apply messages and every configuration-derived field remain loaderless.
  • Refuse all symlinks. Every component of an include path is checked at the one confinement seam.
  • Any confined root-relative file. Root-level and nested paths of any extension are accepted; there is no partials/ prefix rule.

No choice adds a timeout, permission/access change, pinned runtime version check, or subprocess integration.

Access-policy disclosure (separate)

  • no new reach Includes resolve only inside the selected template root, which is already Toha's confinement boundary for source files, files: rule sources, YAML !include, and hook scripts.
  • no timeout no permissions change no pinned check no subprocess
  • accepted The static closure enables the minijinja unstable_machinery build feature (a no-semver-guarantee crate API) — a dependency/maintenance risk, not an operator capability change.
