Toha 0.2.0 · Approved design brief

Jinja {% include %} within the template root

Turn on Jinja includes for rendered file bodies, confined to the selected template root, without granting arbitrary filesystem access and without disturbing the separate YAML !include.

design-only second release implementation-ready approved choices

Task — author outcome

Let a template author factor shared text into any confined root-relative file and pull it into a rendered file body with Jinja {% include %}.

  • Any path under the root. Valid examples include notice.txt, shared/legal/license.inc, and partials/frontmatter.md. No prefix or extension allowlist.
  • Rendered file bodies only. Source-tree and files: bodies get includes. Configuration, fields, paths, hooks, and messages do not.
  • Predictable fallback. One literal name or an ordered literal list. The first existing file wins; ignore missing emits nothing only when every candidate is absent.

Base candidate C2 (capability-by-type) + selected graft of C1 (compile-time confined closure).

Task — boundaries

  • template.yml and YAML !include documents remain configuration parsed as data. Generated .yml/.yaml file bodies still get Jinja includes.
  • Included content stays inside the selected template root. Reject absolute paths, .., backslash separators, and every symlink component.
  • Preserve YAML !include as a separate feature with separate diagnostics.
  • Design only. The paired implementation owns canonical specification, guide, and example edits; no schema shape changes.

Full package: docs/technical-designs/second-release/jinja-includes/.

Pre-mortem — boundary failures

  • Confinement bypass. A symlink inside the root points outside. Mitigation: canonicalize, require starts_with(root), and refuse every symlink component.
  • Scope creep onto the interview. Crate-wide grammar reaches configuration fields. Mitigation: only FileTmpl admits include; ordinary Tmpl rejects every multi-template statement.
  • Sibling grammar leaks. Enabling MiniJinja includes also enables block/import/from-import/extends. Mitigation: reject those AST statements before registering any partial.
  • Diagnostics collide. A Jinja message looks like YAML !include. Mitigation: every new message says “jinja include”.

Pre-mortem — lifecycle failures

  • Late files: failure. A missing partial is found only after the interview. Mitigation: Template::load compiles and stores every files: body before a driver can start or replay an interview.
  • Fallback changes meaning. The first absent candidate fails before the second is tried, or ignore missing hides a confinement error. Mitigation: preserve MiniJinja's ordered not-found-only fallback boundary.
  • Silent cycles. A cycle degrades to a recursion-limit message. Mitigation: the static closure names the cycle path before rendering.
  • Dependency churn. AST inspection uses MiniJinja's unstable machinery. Mitigation: isolate it behind Partials and bind both required features explicitly.

Module and ownership seam

Template::load creates the root-bound capability once. A files: rule keeps its compiled body through the interview; source-tree bodies use the same capability when planning discovers them.

Template::load
  ├─ root = folder.canonicalize()                 [existing]
  ├─ partials = Partials::rooted(&root)            [Template owns]
  ├─ Builder { partials: &partials }
  │    └─ files: source ─▶ partials.compile(...)
  │         ├─ complete AST gate
  │         ├─ confined literal closure + reference union
  │         └─ FileRule.body: FileTmpl             [survives interview]
  └─ config fields ─▶ guarded Tmpl / Expr          [includes refused]

Plan::build
  ├─ walked source ─▶ read_render(..., &template.partials)
  └─ files: rule   ─▶ rule.body.render(...)        [no reread/recompile]

author's root-relative literal name

Public interfaces expected

New types live beside Tmpl. Expr is unchanged. Tmpl stays loaderless and gains an AST mode that rejects every multi-template statement. Only FileTmpl admits include.

Partials — the include boundary

/// Cheap, cloneable handle to the canonical selected template root
/// (consumes selected-template resolution's ResolvedTemplate.folder identity;
/// defines no new one).
/// The ONE seam every include name passes through.
#[derive(Clone, Debug)]
pub struct Partials { root: std::sync::Arc<std::path::PathBuf> }

impl Partials {
    pub fn rooted(root: &std::path::Path) -> Self;         // does not re-canonicalize
    pub fn compile(&self, source: String, label: &str)
        -> Result<FileTmpl, IncludeError>;                 // label = root-relative path, for diagnostics
}

FileTmpl — the capability

/// A compiled file body that MAY resolve {% include %}. A distinct type from
/// Tmpl: holding one IS the include capability; only Partials::compile mints it.
pub struct FileTmpl { /* source, env, referenced_ids */ }

impl FileTmpl {
    pub fn source(&self) -> &str;
    pub fn references(&self) -> &HashSet<String>;          // incl. include-reached ids
    pub fn render<S: Serialize>(&self, ctx: S) -> Result<String, RenderError>;
}

Data structures — failures

Distinct wording from every YAML !include message. No template.yml key is added.

pub enum IncludeError {
    Template(minijinja::Error),
    NotFound { candidates, by },
    Escape { name, by },
    Symlink { name, by },
    NotUtf8 { name, by },
    Unreadable { name, by, source },
    Cycle { path },
    Dynamic { by },
    UnsupportedStatement { statement, surface, by },
}

Single-name and candidate-list not-found messages stay distinct; every new diagnostic says “jinja include” or names the unavailable Jinja statement.

Accepted grammar and closure behavior

  • Accept a literal string or an ordered literal list containing only strings.
  • Select the first confined candidate that exists. Missing earlier candidates are fallbacks; later candidates are not read.
  • ignore missing suppresses only the all-candidates-absent result. It does not hide escape, symlink, read, parse, nested-include, or cycle failures.
  • An empty literal list emits nothing, matching MiniJinja.
  • Reject block/import/from-import/extends anywhere in the AST before registration, including unreachable nested branches.
  • On ordinary Tmpl, reject include and every sibling statement before compiling the internal "value" template.

Direct load-order guards

  • files_include_missing_fails_template_load: call only Template::load; assert the missing target at files[0].source.
  • files_include_reference_fails_template_load: call only Template::load; assert an include-only unknown id while respecting the each binding.
  • files_body_snapshot_is_stable_after_load: change the body and partial after load; planning renders the exact load-owned FileTmpl bytes.
  • The first two tests construct no interview or plan. Restoring loaderless b.tmpl must fail both by name.

Inertness guards — surfaces

  • A source file name and an apply message / interview default containing {% include %} fail as unavailable outside file bodies.
  • include-config-field-inert: a config field names an existing in-root partial and is rejected before lookup. Proves configuration is not a render surface.
  • include-yaml-include-field-inert: the same string delivered into a field through a YAML !include-loaded fragment behaves identically — !include composes data, the field stays loaderless.
  • include-loaderless-self-name-inert: {% include "value" %} is rejected, closing the internal template-name bypass.
  • err-jinja-import-loaderless-self: {% import "value" %} is also rejected.
  • No Jinja-include message equals a YAML !include message; the existing err-include-cycle/err-include-escape fixtures still pass.

Inertness guards — sole-kills

  • Sole-kill: add a partials/-only restriction → both include-root-level and include-nested-outside-partials fail by name.
  • Sole-kill: invert starts_with(root), drop symlink refusal, or drop absolute/../backslash rejection → the matching fixture fails by name.
  • Sole-kill: remove guarded Tmpl's include/import arms → the "value" self-name guards fail.
  • Sole-kill: give a config field FileTmpl → inline and YAML-!include field guards fail.
  • Sole-kill: filter .yml/.yaml bodies or targets → include-yaml-body fails.

Out of scope

  • block, import, from ... import, extends; dynamic targets and lists containing dynamic/non-string items.
  • Jinja include processing of template.yml and any document loaded through its YAML !include tag — configuration is parsed as data, never rendered.
  • Includes on interview fields, expressions, path segments, hook fields, and apply messages.
  • Any change to YAML !include, static, ignore, or path/target confinement; any extension-based rule on which files may be bodies or partials.
  • Any template.yml schema key. Pure interview logic and all terminal/headless/staged/direct/crate paths are preserved.

Reviewer focus — boundaries

  • Escape vectors: absolute, .., and an in-root symlink resolving outside. Try to reach an external file.
  • Surface leakage: can a path, field, message, hook, or YAML configuration document resolve a partial or the internal "value" template?
  • Role vs extension: does a generated YAML body work while YAML configuration remains inert?
  • Sibling grammar: can block/import/from-import/extends use a template registered for include?
  • Diagnostic separation: can a Jinja error be mistaken for YAML !include?

Reviewer focus — lifecycle and semantics

  • Does a files: missing partial or include-only reference fail in Template::load, before interview?
  • Do validation and planning consume the same load-owned body and partial snapshot?
  • Does literal fallback choose the first existing candidate and advance only on not-found?
  • Does ignore missing leave escape, read, parse, nested, and cycle failures visible?
  • Are references unioned across the selected closure, and are cycles named?
  • Does anything attach a loader to the interview engine?

Alternatives explored

CandidateShapeWhy not the base
C1Literal-only compile-time closure, no render loader, template.rootStrongest diagnostics/validation — grafted; final binding requires multi_template + unstable_machinery
C2Capability-by-type (Partials → FileTmpl), render loaderBase: cleanest structural surface enforcement, no unstable dep
C3source_dir root, relative-to-includer, static graphLeaks includes onto interview fields; forces ignore ceremony
C4template.root, relative-to-includer via RefCell loaderRefCell not Sync (set_loader needs Send+Sync); dead symlink check; cycle wording collides

Both scorers ranked C1 > C2 > C3 > C4. Rejected across the board: relative-to-includer (needs name rewriting MiniJinja does not do) and source_dir confinement (no security gain).

Approved choices

  • Static literal closure. Named cycles, author-time confinement errors, load-time reference validation, and no render-time filesystem access.
  • Rendered file bodies only. Apply messages and every configuration-derived field remain loaderless.
  • Refuse all symlinks. Every component of an include path is checked.
  • Any confined root-relative file. Root-level and nested paths of any extension; no partials/ prefix rule.

No choice adds a timeout, permission/access change, pinned runtime check, or subprocess integration.

Implementation-contract completion

  • Feature pair and AST gate. Enable multi_template plus unstable_machinery; admit only include.
  • Two AST modes. Guarded Tmpl rejects all multi-template statements; FileTmpl admits include and rejects siblings.
  • Literal fallback. First existing candidate wins; ignore missing suppresses only exhausted not-found.
  • Load-owned files: body. Compile and validate before interview; retain the same body and partial closure for planning.
  • Plan-owned source-tree body. Compile when walk discovers it, through Template.partials.

Access-policy disclosure (separate)

  • no new reach Includes resolve only inside the selected template root, which is already Toha's confinement boundary for source files, files: rule sources, YAML !include, and hook scripts.
  • no timeout no permissions change no pinned check no subprocess
  • dependency multi_template supplies include parsing/execution. It also exposes sibling statements, which the AST boundary rejects.
  • accepted unstable_machinery supplies the parser/AST with no semver guarantee. It stays isolated behind Partials.
