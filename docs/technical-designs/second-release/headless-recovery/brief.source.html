Toha 0.2.0 · Design brief · decision checkpoint

Finish an incomplete staged interview

Let a person, script, or agent resume saved questions from the target alone, while keeping the same interview engine, saved state, and machine protocol.

3 decisions requested design only implementation waits

Task

Make an incomplete staged interview recoverable without asking the caller to rediscover its template identity.

Today

toha apply --answers answers.json ./output
# refused, although ./output owns a staged interview

Proposed

toha apply --answers answers.json ./output
# resumes, saves accepted answers, and applies when complete

The existing named form remains valid. Exit 4 and non-terminal JSON remain stable. Design basis.

Pre-mortem — the build failed. Why?

  • A rejected answer was saved. Recovery mutated the record before the pure engine accepted the transaction.
  • A machine received prose. Terminal detection replaced JSON for a pipe or redirected file.
  • Two apply spellings drifted. Each route gained its own persistence and error policy.
  • A stop or abort reached planning. A broad result type allowed a non-completion to carry a plannable value.
  • Error attribution was lost. Recovery rebuilt a raw target or flattened configured value origins.
  • Preview changed saved state. CLI --dry-run saved answers or removed an aborted record.

Module and seam

apply / continue
      │ resolve target once; load staged template and origin-bearing defaults
      ▼
existing interview engine ──► Transition { state, accepted answers }
      │
      ▼
cli::recovery::commit_transition   one staged-effect policy
      ├─ Questions ──► cli::presentation ──► terminal summary OR existing JSON
      ├─ Completed ─► existing Plan::build ─► preview OR existing apply
      └─ Ended ─────► stop retains record; abort removes on normal execution

raw Path ─► staging::canonical_target ─► CanonicalTarget used everywhere

The engine remains pure. Recovery owns staged effects. Presentation owns the human and machine views. Planning remains reachable only from completion.

Public interfaces expected

Commands

toha apply --answers FILE PATH
toha apply --answers FILE TEMPLATE PATH
toha continue PATH FILE
  • The first command starts recovery from the staged record.
  • The second asserts that TEMPLATE matches the staged formal identity.
  • The third keeps its one-step continuation behavior.

No new option is added.

Data structures expected

One transition, one staged policy

struct Transition<'a> {
    state: TransitionState<'a>,
    accepted: Vec<Submission>,
}

enum TransitionState<'a> {
    Pending { pending: Box<Pending<'a>>, rejections: Rejections },
    Completed(Completed),
    Ended(Ended),
}

Only answers returned as accepted can reach staged storage.

Planning is completion-only

enum RecoveryOutcome<'a> {
    Questions { pending: Box<Pending<'a>>, record: StagedRecord, .. },
    Completed { completed: Completed, record: Option<StagedRecord> },
    Ended(Ended),
}

Questions and ended runs do not carry Completed. An exhaustive match must select completion before a plan can be built.

One canonical question source

struct QuestionOutput {
    document: serde_json::Value,
    summary: QuestionSummary,
    machine_guidance: Option<String>,
}

The JSON document and terminal summary derive from the same batch, rejections, messages, and parsed command values.

Behaviors to prove

Recovery and transaction safety

ClaimFalsifying observation
Both apply spellings are equivalent after identity selectionDifferent JSON, state, files, hooks, exit code, or error
Unused input is not consumedNo-record, wrong-template, or complete replay opens the file or reads stdin
Rejected input is atomicStored submission bytes change after rejection
Accepted prefixes survive later failureA planning, trust, conflict, file, or hook failure loses accepted answers

Flow result compatibility

ResultExpected staged and target effects
PendingSave accepted prefix; no plan; exit 4
ProceedSave, plan, apply; remove record only after success
Flow dry-runSave, show plan; no file or hook; keep record
StopSave; no plan; keep record
AbortNo plan; normal execution removes the record
CLI --dry-runSimulate any result; change no staged or target state

Protocol and authority guards

  • Piped or redirected question output is byte-equal to the existing protocol serializer.
  • stage --async stays JSON through a pseudoterminal.
  • All path spellings carry one CanonicalTarget through load, save, context, plan, apply, abort, and cleanup.
  • Configured-default warnings and failures keep their exact origin through both apply spellings.
  • Removing the Ended match arm fails compilation after the flow types land.

Out of scope

  • The interview engine, flow-node meaning, and ordinary confirm values.
  • The wire schema and staged-record schema.
  • Preset selection, configured-origin ownership, and target normalization.
  • Trust, hook, conflict, partial-write, and cleanup policies outside recovery routing.
  • New output flags, permissions, access rules, timeouts, version pins, or application subprocesses.

The accepted flow design and integrated error producer remain the authorities: error producer.

Reviewer focus — what to attack

  • Find a route that bypasses commit_transition. Claim: apply and continue share the staged-effect policy.
  • Make rejected data persist. Claim: only the engine's returned accepted prefix can be saved.
  • Reach planning from pending, stop, or abort. Claim: the types prevent it.
  • Make a pipe receive prose or async staging receive prose. Claim: only question results from apply and continue inspect stdout.
  • Find a second target or origin authority. Claim: recovery accepts the existing typed values unchanged.
  • Make preview mutate staged bytes. Claim: CLI --dry-run suppresses every staged effect.

Alternatives explored

AlternativeWhy it is not the proposed base
One broad command executor for apply and continueMoves established routing without hiding more policy
Run continue, then applyCreates two transactions and an intermediate failure point
Keep the target-only refusalForces rediscovery of identity already owned by the staged target
Always print JSONLeaves terminal users with a protocol document instead of a recovery instruction
Add --json or --outputExpands the command surface when non-terminal stdout already preserves JSON

Two structurally distinct candidates and an independent cross-judge informed the synthesis. The focused recovery seam is the base; the shared transition policy and completion-only planning guard are grafted from the broader design.

Decisions needed first

1 — Target-only answers

1A — Resume and apply (recommended).

apply PATH --answers FILE uses the staged record at PATH, saves accepted progress, and applies on completion.

1B — Keep the refusal.

Require continue PATH FILE or a repeated template operand.

Recommend 1A so the target identity that already exists can drive recovery.

2 — Exit-4 output on a terminal

2A — Show a concise summary (recommended).

Apply and continue show missing answers and the next command. Piped or redirected stdout remains JSON. stage --async always remains JSON.

2B — Always show JSON.

Keep the current representation on terminals and non-terminals.

2A changes terminal stdout for exit-4 question results. Exit 4 and non-terminal JSON do not change.

3 — Named recovery

3A — Preserve same-template resume (recommended).

The template operand is an identity assertion. A match enters the same recovery path as target-only apply.

3B — Refuse named recovery.

Require target-only recovery or continue whenever staged state exists.

Recommend 3A to preserve the supported route and make both apply forms equivalent after identity selection.

Size

Expected implementation: one focused agent-day plus independent review.

  • Private recovery and presentation modules.
  • Apply and continue routing changes.
  • Command, protocol, architecture, and guide updates.
  • Route-equivalence, failure-injection, pseudoterminal, and compile-fail guards.

The implementation starts only after approval of this exact revision.

Complexity with this plan

Moderate.

  • The interview and wire formats stay unchanged.
  • One typed transition seam concentrates persistence and flow-result handling.
  • One presentation result selects terminal prose or existing JSON.
  • The largest proof burden is route equivalence across success, rejection, and downstream failure.
