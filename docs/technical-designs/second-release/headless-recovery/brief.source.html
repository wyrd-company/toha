Toha 0.2.0 · Revised design checkpoint

One route per caller

Scripts, agents, and people each get their own command path. Every answers file names the template it answers.

route model decided template identity decided exact revision needs approval design only

Task

Require template identity in every answers file, and give each kind of caller one clear path to finish an interview and apply it.

Current file

{
  "label": "Sample",
  "quantity": 4
}

Question ids can accidentally fit another template.

Designed file

{
  "template": "forge:catalog/receipt@stable",
  "answers": {
    "label": "Sample",
    "quantity": 4
  }
}

The template must match before any answer is evaluated.

The original problem, reassessed

The rough edge came from the agent that tested headless paths during 0.1.0 acceptance. A partial apply --answers exited 4, listed the next questions as errors, and put the recovery commands on stderr only.

Original questionResolution
Target-only apply P --answers F?Not needed. Agents use continue P F, then apply P.
Exit-4 output on a terminal?Not a rendering problem. Each route reports one meaning to one kind of caller.
Named apply on a staged interview?Kept for people: apply T P prompts, then applies.

Agent route

Stage, then answer batch by batch

$ toha stage forge:catalog/receipt@stable ./output --async
{ "protocol": 1, "status": "questions", "schema": { ... }, ... }

answer these questions with an answers document:
  {"template": "forge:catalog/receipt@stable", "answers": { ... }}
then run: toha continue ./output <ANSWERS> (- reads standard input)
$ echo $?
4

stage --async FILE writes the question JSON to FILE and the instructions to stdout.

Complete, then apply

$ toha continue ./output answers.json
the interview at ./output is complete
to see the files it will write: toha apply ./output --dry-run
to write them: toha apply ./output
$ echo $?
0
  • A question not yet answered is the next step, not an error.
  • Rejected answers come back with their errors; nothing is saved.
  • apply P on an incomplete interview never prompts. It shows the batch and both continue forms.

Scripted route

One shot, one JSON document

$ toha apply forge:catalog/receipt@stable ./output --answers answers.json
{ "protocol": 1, "status": "applied", "context": { ... },
  "files": [ { "action": "create", "path": "README.txt" } ], ... }
  • Never creates, changes, or removes staged state.
  • Refuses when an interview is staged at the path, before reading the file.
  • Writes exactly one JSON document to stdout, and nothing else.

Person route

  • apply T P — the direct route. Prompts, saves at each batch, applies at the end. Resumes a staged interview of the same template.
  • stage T P — prompts and saves at each batch. At the end shows the dry-run plan and how to apply.
  • continue P — recovery after Ctrl-C or a fault. Same saving and ending as stage.

After an interrupt, continue P and apply T P both pick up from the last saved batch.

Without a terminal, these refuse and name the agent route.

Pre-mortem — the build failed. Why?

  • The wrong template accepted the file. Question ids matched before identity was checked.
  • A script left staged state behind. The one-shot route saved a partial interview.
  • An agent hung at a prompt. A route guessed "person" from a pseudo-terminal.
  • A script could not parse the output. A warning or instruction line leaked into stdout.
  • A crate caller bypassed the check. A public parser returned raw answers.
  • A mismatch changed state. Staged answers, flow, plan, files, or hooks ran before the check.

        question JSON + text           one JSON result document

Protocol owns the file boundary and result documents. The CLI owns routes, instructions, and exit codes. The interview engine stays pure.

One identity authority

  • The source resolver produces the formal template name.
  • The staged record stores that same name.
  • Question output publishes it as context.template.
  • The answers file copies that exact string.
  • Toha compares strings. It never resolves the file's declaration.

Accepted

"template": "forge:catalog/receipt@stable"

Rejected

"template": "receipt"

An alias is not the emitted formal name.

Public interfaces expected

Commands that read an answers file

toha apply TEMPLATE PATH --answers FILE   # compares with the command template
toha continue PATH FILE                   # compares with the staged template

No other route reads an answers file.

Crate document operations

answer_document_once(expected_template, pending, text)
    -> Result<DocumentStep, SubmitDocumentError>

answer_document_headless(expected_template, template, interview, text)
    -> Result<Headless, SubmitDocumentError>

Both parse and compare internally. No verified value can be extracted and submitted to another interview.

In-memory RawAnswers, Pending::answer, and raw headless driving remain. The public raw JSON parser is replaced.

Private identity capability

struct VerifiedSubmission {
    raw: RawAnswers,
    stored: Submission,
}

fn parse_and_verify(expected_template: &str, text: &str)
    -> Result<VerifiedSubmission, AnswersDocumentError>;

Private, no unchecked constructor, consumed by the operation that creates it.

Validation order

  1. Establish target and staged state; refuse a wrong-time request before opening the file.
  2. Establish source, template, configured values, and start or replay.
  3. Read once; validate JSON and the two-field envelope.
  4. Recognize a legacy bare map and show the wrapper to use.
  5. Compare the declared template with the established formal name.
  6. Only then parse question ids and enter the interview engine.

The file boundary came from a two-candidate arena with an other-family judge. The route model is Bob's decision; it changes which routes use the boundary, not the boundary.

Decisions

Decided in discussion:

  • One route per caller; no terminal-status guessing.
  • Scripted route never stages, refuses on staged state, and writes one JSON result for every outcome.
  • Agent output is question JSON plus text instructions; completion is instructions only.
  • Direct apply T P saves at each batch and resumes.
