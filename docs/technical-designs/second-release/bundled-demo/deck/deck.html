Toha 0.2.0 · design brief · task 1074

Bundled offline toha-demo

Resolve and run the demo template by name — offline, from any directory, on first run — behind one CLI resolution seam.

architect Phase C awaiting Bob's exact-revision approval paired impl: 1059

Task

Make Toha's small inspectable demo resolvable and runnable by name, offline, from any directory, on first run — with no registry entry, no cache warm-up, no network, and no git.

Today the demo lives only at docs/examples/demo/ and ships in the crate tarball; it is not compiled into the binary, so toha apply toha-demo fails with "template not found" on a clean machine.

  • Covers apply, apply --dry-run (the preview path), and stage → continue/apply across separate processes.
  • This is a design task. Phase D (implementation) belongs to task 1059.

Pre-mortem — the design and implementation failed. Why?

  • It shadowed a real template. A user's installed or aliased toha-demo silently changed meaning. Guarded: fallback-only — the bundled branch fires only on the exact NotFound("toha-demo") that fails today; the registry is consulted unchanged and always wins.
  • "Embedded" leaked into the pipeline. The engine, Plan, apply, protocol, or staging learned about embedding. Guarded: the word lives only in src/cli/bundled.rs; ResolvedTemplate gains no field.
  • Resume broke offline. A staged interview could not be reconstructed in a later process. Guarded: identity (formal_name, commit) re-materializes from the embedded bytes with no network or registry.
  • The copy drifted. The embedded demo diverged from the documented example. Guarded: include_dir! makes the embed the source; the commit is derived from those bytes at runtime.
  • It needed an approval nobody gave. A new permission, timeout, pinned check, or subprocess slipped in. Guarded: writes only where git already writes; no new capability.

Public interfaces expected

New module — src/cli/bundled.rs

/// Reserved resolution token and the demo's stable formal name.
pub const RESERVED: &str = "toha-demo";

/// The single maintained source, embedded at compile time.
static DEMO: Dir<'static> = include_dir!("$CARGO_MANIFEST_DIR/docs/examples/demo");

/// Content version: sha256 hex over the embedded tree, derived once at runtime.
pub fn commit() -> &'static str;

/// First-run resolve: materialize + describe. Called only after every registry
/// layer returned NotFound for exactly RESERVED.
pub fn resolve(dirs: &Dirs) -> Result<ResolvedTemplate, ResolveError>;

/// Reconstruct from a staged identity, offline. None => not the bundled record,
/// so resume_template falls through to its existing paths.
pub fn resume(formal: &str, commit: &str, dirs: &Dirs)
    -> Option<Result<ResolvedTemplate, ResolveError>>;

/// Read-only descriptor for the templates-list row (D3). Not a registry entry.
pub fn listing_row() -> BundledRow;

Out of scope

  • The pure interview engine, Template, Plan, apply, protocol, staging.
  • The ResolvedTemplate shape, the <TEMPLATE> classification order, the trust model, path safety, no-overwrite-without---force.
  • The toha library crate. No new subcommand; no preview command (--dry-run is preview).
  • Production and specification/schema edits — described here, applied by 1059.

Reviewer focus — attack these

  • Can any current name-resolution outcome change? Try installed / aliased / discovered / short-name toha-demo and bare demo.
  • Does the fallback fire on Ambiguous or any non-toha-demo NotFound? It must not.
  • Is the resume guard load-bearing — does a mismatched commit refuse rather than emit different files?
  • Is materialization genuinely idempotent and race-safe under concurrent processes?
  • Does anything below the seam gain knowledge of embedding?
  • Does writing the cache (or the D2 temp fallback) introduce a capability needing approval?

Decisions needed first

  • D1 — Collision precedence. recommend: fallback-only Preserves every current outcome, no approval. Alternative: reserved-name-wins narrows resolution → needs approval.
  • D2 — Cache-unwritable behaviour. recommend: fail clearly Keeps writes inside the documented cache. Alternative: degrade to a temp dir new write location outside the cache → disclosable capability question.
  • D3 — Discoverability. recommend: show One read-only bundled row in unfiltered templates list; additive, changes no resolution outcome.
  • D4 — Downstream identity. Confirm formal_name="toha-demo" + commit=<content digest> is the coordination surface designs 1073 (defaults) and 1075 (Jinja context) key on.

Deck inclusion is not approval. Any capability restriction, permissions/access, timeout, pinned check, or subprocess needs separate explicit approval — none is introduced under the recommended options.

Size and complexity

Size: ~M. One ~150-line module, three small resolution branches, one presentation row, and the test suite (two unit + one integration fixture with a cross-process variant), plus canonical-document updates owned by 1059.

Complexity: moderate. The hard parts — content-addressed idempotent materialization and offline identity reconstruction — reuse proven patterns (skills::export, the git source cache, the existing resume path). No new concurrency, no new capability, no engine change.
