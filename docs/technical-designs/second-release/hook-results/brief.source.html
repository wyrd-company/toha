Let a template read what a hook did

A hook can opt in to expose its exit code and output, so a later hook or the closing message can react to it — without changing trust and without ever writing command output into generated files.

architect design Phase C checkpoint needs your decisions no runtime changes yet

Task — react to a hook's result

Toha hooks are commands run after files are written (for example git init). Today a hook can only pass or fail; nothing a template author writes can see what a hook did.

Authors want to

  • Run a later hook only if an earlier one succeeded
  • Pass an earlier hook's output to a later command
  • Report a result in the closing message

This design adds, opt-in

  • A hook id
  • Reading id.exit_code, id.stdout, id.stderr
  • Nothing changes for a hook without an id

Before and after — a conditional hook

Before — no way to branch

hooks:
  - run: [ lint-tool, --check, . ]
  - run: [ test-tool ]

# A failing lint stops everything.
# You cannot "fix, then test".

After — read the result

hooks:
  - id: lint
    run: [ lint-tool, --check, . ]
    allow-failure: true
  - run: [ lint-tool, --fix, . ]
    when: "lint.exit_code != 0"
  - run: [ test-tool ]
    when: "lint.exit_code == 0"

A hook opts in with id. Only later hooks and the closing message can read it.

Before and after — use a hook's output

Before

hooks:
  - run: [ git, describe, --tags ]

# The version prints to the screen
# and is then gone.

After

hooks:
  - id: version
    run: [ git, describe, --tags ]
    capture: [ stdout ]
messages:
  after-apply: "Created at {{ version.stdout }}."

capture names the streams the template reads. Captured output is not printed by Toha; it appears only where the template places it.

Before and after — read the output as JSON

Before — parse it yourself

hooks:
  - id: pkg
    run: [ pkg-tool, info, --json ]
    capture: [ stdout ]
# You get the raw text in pkg.stdout
# and must parse it inside the template.

After — parse: json

hooks:
  - id: pkg
    run: [ pkg-tool, info, --json ]
    parse: json
    capture: [ stdout ]
messages:
  after-apply: "Built {{ pkg.name }} {{ pkg.version }}."

With parse: json, the parsed value is pkg itself — pkg.name, pkg.tags[0]. Bob's requested addition.

Pre-mortem — how this could go wrong

Imagine the design and build failed. The likely causes, and the guard the design puts against each:

FailureGuard in the design
A hook's output silently lands in a generated file Files can never read a result; only later hooks and the closing message can
Exposing output quietly weakens "a failed hook stops the run" The stop-and-fail default is unchanged; tolerating a failure is a separate, explicit opt-in that must be read
A new field slips past template trust review The new fields are already inside the reviewed hook fingerprint; a test fails if a future field escapes it
A template reads a result that does not exist yet Rejected when the template loads, before anything runs
A new name clashes with an existing template No new reserved name; a hook id is an ordinary name with the existing duplicate rule

Module and seam — where the work sits

The change lives in the phase that already runs hooks. The interview engine, staging, replay, and trust are untouched.

Template load   check every result read: exists, captured, comes
                after its hook, on an allowed surface  (before anything runs)
      |
Plan build      hooks/messages that read no result render as today;
                the few that do are held back
      |
Apply (writes)  write files, then for each hook:
                  render the held-back parts against results so far
                  run the hook, record {exit_code, stdout, stderr}
                then render the closing message
                  --> results are used here and discarded; never saved

One place does the interleave (apply). Everything else is a load-time check.

What stays exactly as it is

  • The pure interview engine reads nothing from the machine
  • Staging, resume, and replay — unchanged; results are never saved
  • Template trust and the reviewed hook fingerprint — unchanged
  • The seventeen reserved context names and every other approved rule

What an author writes (1 of 2)

Three optional hook fields. Absent them, a hook behaves exactly as today.

FieldMeaning
idNames the hook so its result can be read as id.exit_code / id.stdout / id.stderr
captureThe output streams to keep: [stdout], [stderr], or both. Required to read a stream
allow-failureTolerate a nonzero exit so a later hook can react to it. Must be read somewhere
parse: jsonParse stdout as JSON, so the parsed value is id itself. Requires capture: [stdout]
status-idWith parse: json, the name that carries the exit code and raw output (so JSON keys never clash with them)

Where a result can be read (2 of 2)

Can read a result

  • A later hook's condition
  • A later hook's arguments and working directory
  • The closing after-apply message

Cannot read a result

  • Generated files and their paths
  • The opening message and interview questions
  • The program name of a hook, and each lists

A result is a plain value named after the hook's id. There is no new reserved word.

Data shapes — the result value

A result read as id.<field> is an object with exactly three fields:

exit_code: 0        # the number the command returned;
                    # empty (none) means the hook did not run
stdout: "v1.2.3"    # present only if capture includes stdout
stderr: ""          # present only if capture includes stderr
  • exit_code is none means "did not run" (its condition was false)
  • exit_code == 0 means it ran and succeeded
  • Output is decoded as text; non-text output fails the run with a clear message and never leaks bytes

Data shapes — a JSON result

With parse: json, id is the parsed value; its type follows the JSON:

OutputRead as
{"name":"demo"}id.name
["a","b"]id[0], id | length
"stable" / 3 / true the value itself
nullid is none
  • Empty or malformed JSON (on success) fails the run with a clear message and no leaked bytes
  • A hook that did not run reads as empty; the status-id tells "did not run" from "ran but printed no JSON"
  • Uses the JSON library already in Toha — no new dependency

Data shapes — under the hood (for the build)

For the implementer and reviewer; a manager can skip this.

// The hook node gains three opt-in fields.
struct HookNode { /* … */ id: Option<Id>, capture: Capture, allow_failure: bool }

// The outcome carries captured streams; its Debug never prints them.
struct HookOutcome { success: bool, code: Option<i32>,
                     stdout: Option<String>, stderr: Option<String> }

// A surface is rendered now, or held for the apply loop.
enum Planned<T> { Ready(T), AfterHooks(Deferred) }

Results live only inside apply and are dropped when it returns. Nothing is added to the saved staging record.

Behaviors to prove (1 of 2)

Each is falsifiable — the fixture fails if the behavior is wrong.

BehaviorHow it could fail
A later hook runs or is skipped by an earlier hook's exit code The wrong branch runs
Captured stdout appears in a later argument and the message Wrong or empty text
A failed hook still stops the run by default Removing the guard lets it continue — a named test must fail
Tolerating a failure needs an explicit, read opt-in A silent weakening slips through

Behaviors to prove (2 of 2)

BehaviorHow it could fail
Reading an uncaptured, forward, or unknown result is rejected at loadA typo is silently empty at runtime
A hook that did not run reads as empty, never an error An undefined value crashes the render
Non-text output fails cleanly with no leaked bytes Corrupted text flows into a command
A hook with no id behaves byte-for-byte as today Existing templates change behavior
A dry run lists every hook and runs none A hook runs during preview

Out of scope

  • Reading a result in files, the opening message, questions, a hook's program name, or each lists
  • Any new reserved word or change to the seventeen context names
  • Saving results, or any change to staging, resume, or replay
  • A limit on captured output size (would be a new policy — ask if wanted)
  • Any new trust, permission, timeout, version pin, or subprocess policy
  • The canonical spec, schema, guide, and example edits — owned by the paired implementation (1063)

Reviewer focus — attack these

  • Can any output reach a generated file or public text? (should be impossible)
  • Can capturing a stream silently change whether a program sees a terminal, without trust re-review?
  • Is a result ever readable before its hook runs, on any surface?
  • Does a failed hook still stop the run unless explicitly tolerated?
  • Do the new fields stay inside the reviewed hook fingerprint?
  • Does replay or resume still read nothing live?

Alternatives explored

Five candidate designs — three in-house and two written independently and blind, then scored by an independent judge.

ShapeWhy not chosen
A new hooks/results namespace Would add a reserved word and break existing templates that use that name
Infer capture from what is read An edit elsewhere could quietly change a hook's output behavior, outside trust review
A "did it run / did it pass" pair of fields Redundant once a signal is always fatal and "empty" means "did not run"
Named execution "stages" A second ordering that just repeats list order
Read results only in conditions and the message (narrow) Cannot pass output to a later command — a decision for you (below)

The chosen shape takes the smallest surface from one and the static safety and trust posture from the other.

Decisions needed first

Five rulings before the build starts. Recommendations given. Your JSON request approves none of the first three by itself.

  1. How much can read a result? — see next slide
  2. A hook id is an ordinary name, sharing the space of question and data names (a clash is the existing duplicate error). Recommended: yes — it avoids a new reserved word.
  3. Non-text output (and malformed JSON) fails the run with a clear message. Recommended: yes — the alternative silently corrupts text that may become a command argument.
  4. The JSON mode shape — see the JSON decisions slide.
  5. JSON capture — parse: json requires an explicit capture: [stdout]. Recommended: yes — one place controls what is piped.

Decision 1 — how much can read a result

Broad recommended

Later hooks (condition, arguments, working directory) and the closing message.

  • Meets the goal: pass output to a later command
  • A hook's program name and each stay fixed, so a dry run still lists every command

Narrow

Only conditions and the closing message.

  • Cannot pass output to a later command
  • That case would need a wrapper script instead

Disclosure: broad lets a hook's output become a later command's argument. The author writes that, and the text comes from the hook's own environment; hooks already require trust. This adds a new ability; it removes nothing. Files and the opening message are excluded either way.

Decision 4 — the JSON mode shape

Your requested addition, as designed:

  • parse: json makes the parsed value id itself — id.name, id.tags[0] — not hidden under a sub-property.
  • The exit code and raw output move to a name you pick, status-id, so a JSON key can never clash with them. You only need it when a hook may not run or may fail.
  • "Did not run" reads as empty (not undefined); status-id tells that apart from a hook that ran but printed no JSON.

Approve this exact shape. Uses the JSON library already in Toha — no new dependency, no new limits.

Size

Expected implementation effort for the paired task (1063): about one to two focused days for an agent.

  • Load-time checks and the new fields — the largest part
  • Holding back and rendering the few result-reading parts in the apply loop
  • Capturing output in the process runner
  • Fixtures for each behavior, plus the trust-coverage guard test
  • Spec, schema, guide, and example updates

Complexity

Moderate. The risk is concentrated and understood.

  • One new interleave (run a hook, then render the next part) in a single place
  • Load-time checks reuse the analysis the context design already built — no new machinery
  • The trust story needs no change: the new fields are already covered, and a program name can never come from output
  • Everything is opt-in, so existing templates are unaffected
