## jaq (jaq-core / jaq-json / jaq-std / jaq-fmts)

- Cloned revision: `f167ad43872b14ef4355922331830571ddbe7dae` (2026-08-28 18:01:33 +0200). No tags on this shallow clone.
- Crate versions (from workspace `Cargo.toml`): `jaq-core 3.1.1`, `jaq-std 3.0.3`, `jaq-json 2.0.3`, `jaq-fmts 0.1.1`, `jaq-all 0.3.0` (meta-crate bundling all of the above plus formats).
- **Verdict: RESERIALIZES (pure transformer). Not format-preserving.**

### Embeddable library surface
- `jaq-core`: interpreter for the jq/jaq filter language, generic over a value type via the `ValT` trait (`/workspaces/references/toha/jaq/jaq-core/src/val.rs:55`).
- `jaq-json`: default JSON-superset value type `Val` (`/workspaces/references/toha/jaq/jaq-json/src/lib.rs:46-67`) implementing `ValT` (`lib.rs:133`) and `jaq_std::ValT` (`lib.rs:301`).
- `jaq-std`: standard library of jq filters.
- `jaq-fmts`: multi-format (de)serialization — TOML, YAML, XML, CBOR, CSV/TSV, in addition to JSON (`/workspaces/references/toha/jaq/jaq-fmts/src/lib.rs:54`, `Format::from_str` at lines 59-79 recognizes `cbor`, `toml`, `xml`/`xhtml`, `yml`/`yaml`).
- `jaq-all`: convenience crate that re-exports `jaq-core + jaq-std + jaq-json + jaq-fmts` behind features `formats` / `std-all` (`/workspaces/references/toha/jaq/jaq-all/Cargo.toml`).

### Value type
- `pub enum Val { Null, Bool(bool), Num(Num), BStr(Box<Bytes>), TStr(Box<Bytes>), Arr(Rc<Vec<Val>>), Obj(Rc<Map<Val, Val>>) }` — `/workspaces/references/toha/jaq/jaq-json/src/lib.rs:46-67`.
- Object storage: `pub type Map<K = Val, V = K> = indexmap::IndexMap<K, V, foldhash::fast::RandomState>;` — `jaq-json/src/lib.rs:117`. This means **insertion order of keys is preserved in memory** (IndexMap), unless the caller requests `sort_keys` at print time (see below).

### Parsing discards comments; no CST
`/workspaces/references/toha/jaq/jaq-json/src/read.rs:10-19`:
```rust
/// Eat whitespace/comments, then peek at next character.
fn ws_tk<L: Lex>(lexer: &mut L) -> Option<u8> {
    loop {
        lexer.eat_whitespace();
        match lexer.peek_next() {
            Some(b'#') => lexer.skip_until(|c| c == b'\n'),
            next => return next,
        }
    }
}
```
`#`-style comments (jq/jaq's JSON-superset extension) are scanned and **thrown away** during lexing — they never enter the `Val` tree, there is no separate comments/trivia channel, and no CST/AST with source ranges is produced. `parse_single` / `parse_many` (`read.rs:35-50`) return only `Val`. There is no `json5`-specific input mode; the informal "superset" (`#` comments, byte strings `b"..."`, `NaN`/`Infinity` literals, non-string object keys) is not JSON5.

### Serialization/printing code (reserialization, not preservation)
`/workspaces/references/toha/jaq/jaq-json/src/write.rs`:
- `format_val!` macro (lines 202-260) walks the `Val` tree fresh and emits JSON syntax from scratch, driven by a `Pp` (pretty-printer) struct (lines 162-175: `indent`, `sort_keys`, `styles`, `sep_space`).
- Public entry points: `pub fn write(...)` (line 302, std/io::Write), `write_buf` (line 321), and the `Display for Val` impl (line 796-800) which calls `write::format`.
- `Val::to_json(&self) -> Vec<u8>` (`jaq-json/src/lib.rs:476-480`) builds output via `write::write_buf` with `write::Pp::default()`.
- There is no notion of "original formatting" carried through this path — every byte of output is generated by the pretty-printer from the in-memory value, using generic indent/spacing rules. Two structurally-equal documents with different original whitespace/comments/quote style would serialize identically.

### Formats supported (via jaq-fmts)
`/workspaces/references/toha/jaq/jaq-fmts/src/lib.rs:54,59-79`: `raw, raw0, json, cbor, yaml, toml, xml, csv, tsv` — but these are all round-tripped through the same `Val` type and the same reserializing writer; none of them preserve original formatting/comments either (TOML support here is read/write via `toml-span`, not `toml_edit`, and is one-way transform-and-reserialize, same as JSON).

### Conclusion
jaq is a **jq-language filter engine + reserializer**. It parses input into an in-memory `Val` (order-preserving map, but no comments/trivia/ranges), runs a filter, and prints a brand-new textual representation. It is not suited to "edit one field, keep everything else byte-identical" — comments are unconditionally discarded at parse time and formatting is wholly regenerated at print time.

## jsonc-parser (dprint)

- Cloned revision: `c7d4cf51f772762e00cc22a62b1454e76dfbe5a2` (2026-09-27 17:10:19 +0000).
- Latest tag: `0.34.0` (matches `Cargo.toml` `version = "0.34.0"`, `/workspaces/references/toha/jsonc-parser/Cargo.toml:3`).
- **Verdict: FORMAT-PRESERVING (via an explicit CST edit API, behind the `cst` cargo feature). Also offers PARSE-ONLY value/AST modes.**

### Three parsing modes
1. `parse_to_value` (`src/parse_to_value.rs`) — plain `JsonValue`, no comments, PARSE-ONLY.
2. `parse_to_ast` (`src/parse_to_ast.rs`) — AST with source ranges (`common::Ranged`) and optional comment collection (`CollectOptions { comments: CommentCollectionStrategy, tokens: bool }`), but this is a read-only tree — no mutation API.
3. `cst` module (feature-gated `cst = []`, `src/cst/mod.rs`, 5571 lines) — **the surgical edit API**. Doc comment at the top states the intent directly (`src/cst/mod.rs:1-5`):
   > "CST for manipulating JSONC. Unlike the AST, this keeps every comment and every piece of whitespace, so a document can be edited and written back out with everything the author wrote still in place."

### Core CST types/methods (all cited from `/workspaces/references/toha/jsonc-parser/src/cst/mod.rs`)
- `pub struct CstRootNode(Rc<CstRootNodeInner>)` (line 1107).
  - `CstRootNode::parse(text: &str, parse_options: &ParseOptions) -> Result<Self, ParseError>` (line 1146) — builds the CST by calling `parse_to_ast` internally with `CommentCollectionStrategy::AsTokens` and `tokens: true` (lines 1147-1162), then a `CstBuilder`.
  - `.value() -> Option<CstNode>` (line 1202), `.set_value(root_value: CstInputValue)` (line 1212) — replaces/creates the root value while preserving surrounding trivia (computes `StyleInfo`/indents and reuses the existing newline/trailing-comma style).
  - `.object_value_or_set() -> CstObject` / `.object_value_or_create()` / `.array_value_or_set()` (lines 1259-1317).
  - `impl Display for CstRootNode` (line 1356) — `to_string()` reproduces the full original text plus edits, comments included.
- `CstObject`:
  - `.get(name: &str) -> Option<CstObjectProp>` (line 1764) — looks up a property by decoded name.
  - `.append(prop_name: &str, value: CstInputValue) -> CstObjectProp` (line 1798) and `.insert(index, prop_name, value)` (line 1805) — surgical insertion; `insert_or_append` (line 1809) reuses `ensure_multiline()` and calls `insert_or_append_to_container`.
  - `.properties() -> Vec<CstObjectProp>` (line 1782).
  - `.remove(self)` (line 1885) — calls `remove_comma_separated`.
  - `.sort_properties()` (line 1858) — explicitly documents that it carries each property's leading comments/blank lines and same-line trailing comment along with it when reordering (doc comment lines 1821-1834).
- `CstObjectProp` / value nodes: `.set_value(value: CstInputValue)` variants at lines 1964, 1554, 2315, 2348 (bool/string/number leaf setters) and `.remove(self)` at multiple lines (565, 747, 1008, 1422, 1461, 1493, 1564, 1600, 2084, 2278, 2325, 2358, 2400, 2445) for arrays/objects/tokens/leaves.
- `CstArray::append(&self, value: CstInputValue) -> CstNode` (line 2207).
- The module doc-example (`src/cst/mod.rs:6-33`) shows the full round trip: parse a JSONC doc with a comment, set a nested value, append a new key, and `to_string()` yields the original comment intact plus the new/changed content, byte for byte around the edit.

### JSON5-style leniency (not just JSONC)
`/workspaces/references/toha/jsonc-parser/src/lib.rs:99-124` (`ParseOptions` fields, all default to permissive):
```
allow_comments, allow_loose_object_property_names, allow_trailing_commas,
allow_missing_commas, allow_single_quoted_strings, allow_hexadecimal_numbers,
allow_unary_plus_numbers, allow_bare_decimal_point_numbers,
allow_non_finite_numbers, allow_extended_string_escapes
```
This is effectively a JSON5-superset parser by default (single-quoted strings, hex numbers, unary `+`, bare `.5`, `Infinity`/`NaN`, loose/unquoted-like property names) in addition to JSONC comments/trailing commas — all controllable, and settable to strict-JSON via `ParseOptions { ..all false }` (`src/lib.rs:110-121`).

### Cargo feature required
`Cargo.toml` (`/workspaces/references/toha/jsonc-parser/Cargo.toml:20-27`): `cst = []` is a separate opt-in feature; `preserve_order = ["indexmap"]` and `serde`/`serde_json` are additional optional features for the non-CST value/AST modes.

### Conclusion
`jsonc-parser`'s `cst` module is a direct JSON-family analogue to `toml_edit`: parse once into a full-fidelity concrete syntax tree (including every comment/whitespace token), perform targeted mutations through a typed node API (`get`/`append`/`insert`/`set_value`/`remove`), and print back out with everything untouched preserved. It also natively tolerates JSON5-style syntax on input.

## toml_edit (toml-rs workspace)

- Cloned revision: `e4b8bda51c458b3c9b5671b6ad50a0a4a279f583` (2026-09-18 10:45:21 -0500). No tags on this shallow clone (workspace uses per-crate tags like `toml_edit-v...`, not visible from a depth-1 clone of the tip).
- Crate: `toml_edit` version `0.25.15+spec-1.1.0` (`/workspaces/references/toha/toml-rs/crates/toml_edit/Cargo.toml:3`). Companion `toml` crate (the ergonomic/serde-friendly layer) is version `1.1.6+spec-1.1.0`.
- Package description (from its own `Cargo.toml`, line 4): **"Yet another format-preserving TOML parser."**
- **Verdict: FORMAT-PRESERVING (the reference/gold-standard pattern).**

### Core types (all cited from `/workspaces/references/toha/toml-rs/crates/toml_edit/src/`)
- `pub struct Document<S> { root: Item, trailing: RawString, raw: S }` (`document.rs:8-13`) — immutable/spanned parse result; `Document::parse(raw)` (`document.rs:25`).
- `pub struct DocumentMut { root: Item, trailing: RawString }` (`document.rs:133-137`) — the mutable, editable document. Obtained via `Document::into_mut(self)` (`document.rs:94-100`, calls `despan()` to materialize owned strings from spans) or parsed directly.
  - `.as_table()/.as_table_mut()` (lines 161-170), `.iter()` (line 180) — table access for edits.
- `pub enum Item { None, Value(Value), Table(Table), ArrayOfTables(ArrayOfTables) }` (`item.rs:11-21`) — the "what kind of TOML node is here" model; every table entry carries one of these.
- `pub struct Decor { prefix: Option<RawString>, suffix: Option<RawString> }` (`repr.rs:187-190`) — doc comment: **"A prefix and suffix, Including comments, whitespaces and newlines."** Every `Value`/`Table`/`Array`/`InlineTable` node exposes `.decor()`/`.decor_mut()` (e.g. `value.rs:160-178`, `table.rs:264-269`, `array.rs:80-85`, `inline_table.rs:216-221`) so edits can inspect/preserve/rewrite the exact surrounding comment/whitespace bytes for that node.
- Table preserves declared key order (backed by an internal ordered map keyed through `table.rs`; `Document`/`DocumentMut` `.iter()` walks entries in file order, not sorted).

### How edits preserve comments/whitespace/order
- Every leaf and container node stores its own `Decor` (prefix/suffix raw text) captured verbatim from the source during parsing; only the value itself changes on assignment (e.g. `doc["key"] = value.into()`), and its decor is left untouched unless explicitly rewritten via `.decor_mut()`.
- `RawString` (`raw_string.rs`) holds the literal source span text so unrelated whitespace/comments round-trip byte-for-byte through `Display`/encode (`encode.rs`) rather than being regenerated from a generic pretty-printer.
- This is the direct conceptual counterpart to `jsonc-parser`'s CST: parse once, keep a full-fidelity tree with decor/trivia attached to every node, mutate values in place, re-serialize preserving everything untouched.

### Conclusion
`toml_edit::DocumentMut` is the established "what good looks like" reference for format-preserving structured editing in Rust: parse to a tree that carries `Decor` (comments/whitespace) on every node plus table/array ordering, mutate via typed accessors (`Item`, `Table`, `Value`), and serialize back out with all untouched content intact. `jsonc-parser`'s `cst` module (see above) is architecturally the same pattern applied to the JSON/JSONC/JSON5 family.

## Bottom line for the design

For "edit a JSON/JSONC/JSON5 file in place while preserving comments, key order, and formatting" as an embedded Rust dependency, **`jsonc-parser`'s `cst` module (feature `cst`, crate `jsonc-parser 0.34.0`, https://github.com/dprint/jsonc-parser)** is the correct analogue to `toml_edit`: it is purpose-built for exactly this (see its own doc comment), ships a typed surgical mutation API (`CstRootNode`, `CstObject::get/append/insert/remove`, per-node `set_value`), and additionally tolerates JSON5-style input by default. `jaq` is not a fit for this requirement — it is a filter/query engine that discards comments at parse time and regenerates all output formatting from scratch.
