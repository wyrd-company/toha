Toha 0.2.0 · Content injection design

Add content without taking over the file

Let a template maintain one named part of an existing file while the file owner keeps control of everything else.

approved design implementation next same review draft

Visible regions cover non-JSON text. JSON, JSONC, and JSON5 use one format-preserving structured editor.

What are we trying to enable?

A template can already create a whole file. It cannot safely add one section to a file that somebody else owns.

  • Example: add generated routes to an existing application file.
  • Keep: all text outside the generated section, byte for byte.
  • Repeat safely: applying the same template twice changes the file once.
  • Use the right ownership: visible regions for text; one typed value at a path for the JSON family.

The design is approved. Runtime, specification, schema, guide, and fixture changes belong to the paired build work.

Pre-mortem: what would failure look like?

  • A second run adds the same content again.
  • Toha rewrites line endings, spacing, comments, or keys that it does not own.
  • A person changes content outside Toha's declared ownership and Toha replaces it.
  • A crash leaves half a file on disk.
  • A JSON edit removes comments or reformats the whole document.

How the design prevents those failures

  • Named ownership: visible regions for text; typed paths for JSON-family values.
  • Fingerprint: a checksum records the content Toha last wrote, so repeat and drift are facts rather than guesses.
  • Byte-preserving edit: Toha replaces only the marked range.
  • Plan before write: it resolves every edit before it changes files.
  • Atomic replace: it writes a complete temporary file, then swaps it into place.
  • JSON fidelity: jsonc-parser changes the owned value and retains unrelated source text.

Where the new behavior lives

The interview remains unchanged. The template describes the section, the plan carries it, and apply reads the target file and makes the bounded change.

The file is read only during dry-run or apply. Staged, terminal, headless, direct, and crate callers continue to use the same plan.

Technical seam

  • template reads an injection rule.
  • plan carries a PlannedEdit beside existing whole-file writes.
  • Pure region and JSON resolvers take current bytes in and return a complete candidate file.
  • apply resolves every target in memory before the first write.
  • Plan::mutations() gives project-update work one view of whole-file, region, and JSON-value ownership.

Jinja include/root-boundary work and git-update work touch this shared surface, so their implementations must coordinate before landing.

What a JSON-family author writes

inject:
  - into: "package.json"
    struct:
      path: "scripts.build"
      value: "tsc"

struct selects typed-path ownership for JSON, JSONC, and JSON5. Strings stay strings; boolean, number, null, array, and object values retain their type.

JSON-family targets do not receive Toha marker comments.

What a marked-region author writes

inject:
  - into: "src/app.rs"
    region: "routes"
    when: "add_router"
    source: support/routes.rs
    anchor:
      after: "fn build_router() {"
      occurrence: only

  - into: ".gitignore"
    region: "build-artifacts"
    content: |
      /target
    create: true

region gives the managed section a stable name. anchor chooses its first location. Later runs find the visible markers instead.

What callers observe

  • Dry-run: reports “inject” or “update” with the file and owned region or path.
  • No change: reports nothing for that ownership unit.
  • Changed marked section: stops and names --force.
  • Changed owned JSON value: converges that value without rewriting unrelated source text.
  • Missing anchor: fails without modifying the file.
  • Several matches when one was required: fails as ambiguous.

Existing callers and whole-file behavior stay the same. The new result is included in their normal list of changed files.

    JsonValue { path: &'a TargetPath, json_path: &'a JsonPath },

The pure resolvers prove safe repeat without filesystem setup. The mutation view is derived; it does not replace the current whole-file model.

What a marked-region plan remembers

  • Target: which existing file to edit.
  • Region name: which section Toha owns.
  • Rendered content: what belongs inside that section.
  • Marker style: valid comments for the target format.
  • First-placement rule: anchor or end of file.
  • Create rule: whether a missing target may be created.

It does not remember byte positions. Positions can become stale between planning and applying.

What a JSON-family plan remembers

  • Target: a .json, .jsonc, or .json5 file.
  • Typed path: object keys and existing array indexes.
  • Typed value: string, boolean, number, null, array, or object.
  • Format: strict JSON or permissive JSONC/JSON5 parse rules.
  • Create rule: whether an absent file may start as an empty object.

It does not store byte offsets. jsonc-parser finds the node in the current source during apply.

What appears in the file

// >>> toha:region routes >>>
router.route("/health", get(health));
// <<< toha:end routes sha256:9f2c... <<<
  • The two visible comments define Toha's ownership boundary.
  • The checksum is a fingerprint of the body Toha last wrote.
  • Matching body and fingerprint means “already done.”
  • A mismatch means “somebody changed this section”; Toha stops unless the caller uses --force.

Visible region: author request

inject:
  - into: "config/app.toml"
    region: "features"
    content: |
      analytics_enabled = true
      analytics_sample_rate = 0.1
    anchor:
      after: "[application]"
      occurrence: only

The region name becomes the visible ownership boundary. The anchor is used only for first placement.

Visible region: target before and after

  • BEFORE
    [application]
name = "sample-service"
log_level = "info"
  • AFTER FIRST APPLY
    [application]
# >>> toha:region features >>>
analytics_enabled = true
analytics_sample_rate = 0.1
# <<< toha:end features sha256:a7f3d… <<<
name = "sample-service"
log_level = "info"

Second apply changes no bytes. An edit between the markers produces a conflict instead of a silent overwrite.

JSON-family boundary

JSON, JSONC, and JSON5 use one structured ownership rule. Toha does not add marker comments to any of them.

  • Selected mode: struct: changes one typed value at one path through jsonc-parser.
  • Marker rule: a JSON-family target is rejected during planning with struct: and whole-file guidance.
  • Existing capability: whole-file JSON rendering continues to work.

JSONC and JSON5 comments remain operator source and are preserved by the CST.

JSON-family value: author request

inject:
  - into: "package.json"
    struct:
      path: "scripts.build"
      value: "tsc"

Ownership: Toha owns the value at scripts.build. Every other value and all unrelated source text remain operator-owned.

JSON-family value: target before and after

  • BEFORE
    {
  "name": "sample-app",
  "scripts": {
    "start": "node index.js"
  }
}
  • AFTER
    {
  "name": "sample-app",
  "scripts": {
    "start": "node index.js",
    "build": "tsc"
  }
}

Second apply changes no bytes. If a person changes the owned value, later apply sets it back to "tsc".

The selected editor changes the necessary node and punctuation. In JSONC/JSON5 it preserves unrelated comments, spacing, order, and trailing commas.

One target is resolved and written once

  1. Start with planned whole-file bytes, or read the current target once.
  2. Fold each region or JSON-value edit over one in-memory image.
  3. Stop before any write if any target has an error or unforced region drift.
  4. Atomically replace each changed target once and report its path once.

This makes whole-file-plus-injection and several edits to one file deterministic.

What stays outside this design

  • Combining both the human and generated edits through a three-way merge.
  • A separate toha inject command or a second apply pass.
  • Broad JSON query or filter programs.
  • Structural YAML or TOML mutation; their first release uses marked regions.
  • Changes to the interview engine or existing whole-file conflict rules.
  • Canonical specification, schema, and guide edits in this design branch; the paired implementation owns them.

What reviewers should attack

  • Safe repeat: can any normal replay duplicate or rewrite an unchanged section?
  • Ownership: can Toha alter bytes outside its marked region or typed JSON value?
  • Conflict handling: can --force create a missing section or overwrite unrelated text?
  • Order: do all edits for one path use one current image and one final write?
  • Safety rules: do existing target-path, symbolic-link, and .git checks run before every read and write?
  • JSON fidelity: do JSONC/JSON5 comments and untouched syntax survive inserts and replacements?

        - name: analytics

Ansible: what the target file looks like

  • BEFORE
    services:
  # operator-owned entries
  - name: gateway
    enabled: true
  • AFTER
    services:
# BEGIN MANAGED SERVICES
- name: analytics
  enabled: true
# END MANAGED SERVICES
  # operator-owned entries
  - name: gateway
    enabled: true

The marker pair is the ownership record. A later run finds that pair and replaces the full block.

Ansible: repeat, drift, and limits

  • Repeat: remove the old marked block, insert the declared block, and write only if the complete result differs.
  • Human edit inside the block: no separate drift state; the next run replaces it.
  • Placement: regular expression, beginning, or end. A missing regular-expression match falls back to end of file.
  • Format: text lines outside the block are retained; the feature has no JSON/YAML structure awareness.
  • Write safety: optional backup and validation; temporary-file write followed by atomic move.

What Toha adds: detect drift separately and require explicit --force before replacing it.

The marker is only an insertion point. It does not surround or identify the inserted content.

Scaffold: repeat, drift, and limits

  • Repeat: running the template again inserts the same content again; there is no managed-region identity.
  • Conflict: a missing marker is an error. The implementation uses the first matching line.
  • Format: it copies line text and reuses leading indentation, but its scanner rewrites every line ending to LF and adds a final newline.
  • Scope: available to template scaffolds that add files to an existing project, not whole-project scaffolds.
  • Structure: text insertion only; no JSON/YAML/TOML awareness.

Copier and Cruft: the feature is project update

# Copier records the template source and revision, then:
copier update --defaults --conflict=inline

# Cruft records Cookiecutter template metadata, then:
cruft update --project-dir ./service -y

Both render the old and new template versions, calculate a text difference, and apply that difference to the live project.

Classification: project-wide template update, not direct injection into a named region.

A clean Git patch can retain the operator's unrelated edit while adding the template's new line.

Illustrative target using the native update mechanism. The tools operate on template-version diffs, not YAML fields.

Project update: repeat, conflict, and limits

  • Repeat: when the recorded template revision has no further change, another update produces no diff.
  • Copier conflict: default inline Git conflict markers; optional .rej files.
  • Cruft conflict: try git apply -3, then fall back to .rej files.
  • Format: untouched hunks remain untouched, but neither tool understands document structure.
  • Ownership: the template-version diff, not a stable named region or value path.

Cookiecutter and Kickstart: whole-file generation

cookiecutter https://example.invalid/project-template.git

  • Cookiecutter: renders a file and opens the target for writing; it can skip an existing file, but the inspected generator has no built-in region merge.
  • Kickstart: renders each file and writes through File::create, which replaces an existing target.
  • Classification: whole-file generation. A target “after” is the rendered replacement, not a merge with the previous contents.

Hooks are an escape hatch, not an injection feature

  • COOKIECUTTER
    hooks/
  pre_gen_project.py
  post_gen_project.py
  • KICKSTART
    post_gen_hooks = [
  { name = "finish setup",
    path = "finish_setup.sh" }
]

A hook can edit an existing file because it is an arbitrary script. The author must supply placement, repeat safety, drift detection, conflicts, portability, and format preservation.

Toha comparison: this design supplies those rules as product behavior. It does not propose a subprocess-based injection integration.

Libraries: format-preserving structured edit

  • jsonc-parser for Rust keeps comments and whitespace in a concrete syntax tree, then changes one node. This is the selected JSON-family mechanism.
  • VS Code's node-jsonc-parser returns minimal offset/length/content edits. It is the TypeScript version of the same approach.
  • toml_edit stores formatting on each node. It is the mature TOML analogue.

Classification: implementation mechanisms, not competing template-author features.

jsonc-parser c7d4cf5 · node-jsonc-parser dba4356 · toml_edit e4b8bda

Libraries: whole-document rewrite

  • jaq is a capable query engine, but it drops comments while reading and prints a new document. It is rejected for this feature.
  • serde_json has no comment model; preserving key order does not preserve the original bytes.
  • json5-rs accepts comments as input but does not retain them in an editable document model.
  • npm package-json rewrites the full document while carrying forward detected indentation and newline style.

Classification: implementation mechanisms. They can express broad transformations, but they do not preserve a user-owned source document.

Approved author experience

D1 — A: show visible ownership markers in non-JSON text files.

D2 — A: use one top-level inject list with region: and struct: variants.

D3 — A: infer known non-JSON comment styles, allow an override, and reject an unknown style without one.

JSON-family files use typed-path ownership and do not receive Toha marker comments.

Approved safety defaults

D4 — A: marked-region drift stops; --force replaces only that region.

D5 — A: missing targets require create: true.

D7 — A: resolve every target first, then replace each changed target atomically.

D8 — A: reuse existing sha2 for region fingerprints.

JSON values use declared path ownership and converge without --force.

Approved D6a — option B

Do not support JSON-family marker injection.

  • .json, .jsonc, and .json5 use struct:.
  • A marker rule for those extensions fails during planning with structured and whole-file guidance.
  • Existing whole-file JSON rendering remains available.

Approved D6b — option B

Build structured JSON-family editing in the paired implementation now.

  • Own one typed value at one path.
  • Support strict JSON, JSONC, and JSON5 in the first injection release.
  • Preserve unrelated comments, order, whitespace, and values.
  • Converge an edited owned value; repeated correct state is a byte no-op.

Approved D9 — option B

Use embedded jsonc-parser for structured editing.

It changes the owned node through a full-fidelity CST. It does not run a command or subprocess.

Reject jaq for this feature. Its query engine prints a new document and cannot retain the operator's source fidelity.

Where the complexity sits

The design concentrates format rules in two pure resolvers and keeps file I/O in one grouped apply stage.

  • High: two ownership models, typed-path traversal, CST source preservation, and same-target ordering.
  • Contained: interview behavior and existing whole-file generation stay unchanged.
  • Contained: both modes use the same resolve-before-write and atomic replacement flow.
