Toha 0.2.0 · Design 1068 → Implementation 1031

Content injection into existing files

Toha writes a bounded, idempotently-managed region into a file it does not own — the first mutation past whole-file writes.

revision: jaq & structured mutation, source-cited awaiting Bob's exact-revision approval no runtime / canonical edits

Revision scope: jaq and every alternative JSON-family mutator evaluated against actual cloned source; structured mutation reconsidered (no longer assumed out of scope). The marker base holds; the JSON-family answer and the decided-but-deferred structured mechanism are new.

Task

Design content injection: adding or updating a bounded region of an existing file while leaving the rest to its owner, and hand the mutation contract to the git-update design (1066) and the paired implementation (1031). This task designs; it does not implement.

  • Resolve anchors/selection, idempotency, conflict behavior, ownership of file mutations, and failure/recovery.
  • Preserve the pure interview engine, staging replay, and the TargetPath/symlink/.git safety seams.
  • Acceptance: a template that injects into an existing file, applied twice, changes that file exactly once.

Base chosen by a four-candidate arena (self 30/30, cross-judge 29/30): managed-region markers with a pure resolve_edit and a sha2 end-marker checksum.

Pre-mortem — the design and implementation failed. Why?

  • Idempotency was heuristic. Re-matching injected text drifted once the user edited nearby, so a second apply duplicated or clobbered. killed by a recomputed checksum in the end marker: resolving Toha's own output is Unchanged by construction.
  • Replay diverged. Ownership computed from build-time byte offsets was invalidated by any pre-apply change. killed by selecting the region by marker at apply time; the plan holds no offsets.
  • A user-owned file was silently rewritten. jaq discards comments at lex time (jaq-json/src/read.rs:10-19) and reserializes all output (write.rs:202-260) — a disguised whole-file rewrite. killed by rejecting jaq/reserialize for user-owned files; the structured mode, when it ships, uses jsonc-parser's format-preserving CST.
  • Strict JSON was corrupted by a comment marker. A // marker makes a .json file invalid. killed by a build-time refusal that names the boundary and the author alternatives; JSONC/JSON5 (which allow comments) inject normally.
  • Line endings were renormalized. Editing via lines().join("\n") changed bytes outside the region. killed by byte-range splicing; everything outside the region is preserved verbatim.
  • A half-written user file after a crash. killed by atomic temp-file-plus-rename for injection writes.
  • Whole-file behavior regressed. Collapsing every mutation into one enum changed existence⇒conflict semantics. killed by keeping injection a Plan.edits sibling; the whole-file path is untouched.

Module and seam

No new module. template gains an injection rule; plan gains a PlannedEdit sibling and the pure resolve_edit; apply gains a read-modify-write stage. The engine is untouched. The only target read is at apply/dry-run.

Shared surface named for coordination: Plan + the file-mutation types. 1076 (Jinja includes / root boundaries) and 1066 (git updates) both touch it — coordinate through the board before either lands.

On-disk managed region (single source of truth)

// >>> toha:region routes >>>
    router.route("/health", get(health));
// <<< toha:end routes sha256:9f2c... <<<
//        ^key            ^checksum of the body Toha wrote (existing sha2 dep)

Checksum turns drift detection into a fact: body matches recorded hash ⇒ template changed (replace); differs ⇒ user edit (drift, refuse without --force).

Template config:

      "analytics_enabled": true,
      "analytics_sample_rate": 0.1

BEFORE / AFTER first apply:

  "port": 8080,
  // operator-owned settings
  "log_level": "info"
}
{
  "app_name": "sample-service",
  "port": 8080,
  // operator-owned settings
  "log_level": "info",
  // >>> toha:region features >>>
  "analytics_enabled": true,
  "analytics_sample_rate": 0.1
  // <<< toha:end features sha256:a7f3d… <<<
}

Markers are valid JSONC // comments; operator lines untouched. Second apply with the same answers changes nothing (body hashes to the recorded checksum). Operator edit inside the markers → drift → refuse, name --force.

Strict .json — refused at build time

{
  "version": "1.0",
  // >>> toha:region config >>>   <- would make this INVALID JSON
  "enabled": true
  // <<< toha:end config … <<<
}

Strict JSON has no comment syntax, so marker injection is refused at build time, naming three author alternatives: target a .jsonc/.json5, manage the whole file with files:, or use the deferred structured mode. Not a regression (today Toha cannot inject at all); even npm's own package.json editor reserializes rather than surgically editing strict JSON (npm-package-json/lib/index.js:239-264).

Structured mode (decided mechanism, deferred impl)

Reserved struct: surface — jsonc-parser CST, owns the value at a path:

inject:
  - into: "package.json"       # strict JSON is fine for STRUCTURED mode
    struct: { path: "scripts.build", value: "tsc" }

BEFORE / AFTER (surgical CST edit — only the touched node changes):

{
  "name": "sample-app",
  "scripts": {
    "start": "node index.js"
  }
}
{
  "name": "sample-app",
  "scripts": {
    "start": "node index.js",
    "build": "tsc"
  }
}

Second apply: no bytes change (value already equals desired). For a .jsonc target, comments and trailing commas around the value are preserved verbatim — the property markers jaq would destroy. Ownership = the value at the path; declarative convergence (Toha re-sets exactly its path; strict JSON carries no drift marker). These fixtures belong to the fast-follow, not 1031.

Not out of scope by assumption; deliberately sequenced.

  • Canonical schema/spec/guide edits — owned by the paired implementation (1031).

Reviewer focus

The adversarial reviewer will be told to attack:

  • Idempotency proof. Does Write always recompute the checksum over its emitted body, so re-resolve is provably Unchanged across staging replay?
  • Byte fidelity. Does the region editor splice byte ranges and preserve every byte (line endings, final newline) outside the region?
  • No-silent-overwrite. Can any path let --force rewrite a user-owned file outside its own markers, or fabricate placement?
  • Purity. Does the engine stay free of target reads, and is the only read at apply/dry-run?
  • Composition. Whole-file write then injection into the same file — ordering, and the same-(path,region) duplicate guard.
  • Safety reuse. TargetPath/symlink/.git checks on every edit path, before read and before write.

Decisions needed first

Options + recommendation for each; deck inclusion is not approval.

  • D1 Visible markers written into user files. Recommend: yes (the mechanism).
  • D2 Author surface — top-level inject list as shown. Recommend: adopt.
  • D3 Comment inference + override; unknown extension without override is a load error. Recommend: yes.
  • D4 Drift / --force — drift refuses (exit 1); --force overwrites the managed region only, never fabricates placement. Extends --force (not a restriction). Recommend: adopt.
  • D5 create default false. Recommend: false.
  • D6a JSON family via markers now. JSONC/JSON5 inject via comment markers (in scope, 1031); strict .json is a build-time-refused, documented boundary with named alternatives. Recommend: adopt.
  • D6b Structured "owns-the-value-at-a-path" mode — decided but deferred. Mechanism = jsonc-parser CST (format-preserving), not jaq; implementation is a fast-follow with the struct: seam reserved. Option to pull into 1031 now exists; not recommended.
  • D9 jaq rejected as the structured mechanism. Reserialize destroys a user-owned file's comments/order/format (cited). If structured ships, it uses jsonc-parser's CST. Recommend: reject jaq.
  • D7 Atomic temp-file+rename for injection writes. Recommend: yes.
  • D8 Reuse existing sha2 for the checksum (no new dependency in 1031). The deferred structured mode would add jsonc-parser (embedded, dprint/deno, no subprocess). Recommend: yes.

Size

Medium. Expected agent implementation time for 1031: roughly one to two focused sessions.

  • New: InjectionRule + Builder branch, PlannedEdit, resolve_edit + byte-range region parser, apply stage, FileMutation view, comment table.
  • Canonical edits (1031): template-format spec + schema, CLI spec, architecture design, one guide, and the fixture matrix.

Complexity

Moderate, concentrated in one pure function. The hard logic — placement, idempotency, drift, byte-splice — lives in resolve_edit, which takes bytes in and returns a decision, so it is fixture-testable without the filesystem. The apply integration is a small, ordered stage; the engine and whole-file path are untouched. Risk sits in byte fidelity and the comment-inference table, both directly covered by the behavior matrix.
