Toha 0.2.0 · Content injection design

Add content without taking over the file

Let a template maintain one named part of an existing file while the file owner keeps control of everything else.

decision needed design only same review draft

This revision explains the proposed experience, choices, and tradeoffs in manager-facing language. Technical detail and source research remain in supporting slides.

What are we trying to enable?

A template can already create a whole file. It cannot safely add one section to a file that somebody else owns.

  • Example: add generated routes to an existing application file.
  • Keep: all text outside the generated section, byte for byte.
  • Repeat safely: applying the same template twice changes the file once.
  • Stop on disagreement: if somebody edits the generated section, Toha reports the conflict before writing.

This work designs the feature. Implementation remains in the paired build work after approval.

Pre-mortem: what would failure look like?

  • A second run adds the same content again.
  • Toha rewrites line endings, spacing, comments, or keys that it does not own.
  • A person changes generated content and Toha silently replaces it.
  • A crash leaves half a file on disk.
  • A marker is written into strict JSON, making the file invalid.

How the design prevents those failures

  • Named boundary: visible comments show exactly what Toha owns.
  • Fingerprint: a checksum records the content Toha last wrote, so repeat and drift are facts rather than guesses.
  • Byte-preserving edit: Toha replaces only the marked range.
  • Plan before write: it resolves every edit before it changes files.
  • Atomic replace: it writes a complete temporary file, then swaps it into place.
  • JSON boundary: strict-JSON handling stays a decision; existing whole-file JSON output still works.

Where the new behavior lives

The interview remains unchanged. The template describes the section, the plan carries it, and apply reads the target file and makes the bounded change.

The file is read only during dry-run or apply. Staged, terminal, headless, direct, and crate callers continue to use the same plan.

Technical seam

  • template reads an injection rule.
  • plan carries a PlannedEdit beside existing whole-file writes.
  • resolve_edit is a pure function: current bytes in, write decision out.
  • apply performs the read-modify-write after whole-file writes.
  • Plan::mutations() gives the git-update work one view of whole-file and region changes.

Jinja include/root-boundary work and git-update work touch this shared surface, so their implementations must coordinate before landing.

What a template author writes

inject:
  - into: "src/app.rs"
    region: "routes"
    when: "add_router"
    source: support/routes.rs
    anchor:
      after: "fn build_router() {"
      occurrence: only

  - into: ".gitignore"
    region: "build-artifacts"
    content: |
      /target
    create: true

region gives the managed section a stable name. anchor chooses its first location. Later runs find the visible markers instead.

What callers observe

  • Dry-run: reports “inject” or “update” with the file and region name.
  • No change: reports nothing for that region.
  • Changed generated section: stops and names --force.
  • Missing anchor: fails without modifying the file.
  • Several matches when one was required: fails as ambiguous.

Existing callers and whole-file behavior stay the same. The new result is included in their normal list of changed files.

pub enum FileMutation<'a> {
    Whole { path: &'a TargetPath },
    Region { path: &'a TargetPath, region: &'a RegionKey },
}

The pure function proves safe repeat without filesystem setup. The mutation view is derived; it does not replace the current whole-file model.

What the plan must remember

  • Target: which existing file to edit.
  • Region name: which section Toha owns.
  • Rendered content: what belongs inside that section.
  • Marker style: valid comments for the target format.
  • First-placement rule: anchor or end of file.
  • Create rule: whether a missing target may be created.

It does not remember byte positions. Positions can become stale between planning and applying.

What appears in the file

// >>> toha:region routes >>>
router.route("/health", get(health));
// <<< toha:end routes sha256:9f2c... <<<
  • The two visible comments define Toha's ownership boundary.
  • The checksum is a fingerprint of the body Toha last wrote.
  • Matching body and fingerprint means “already done.”
  • A mismatch means “somebody changed this section”; Toha stops unless the caller uses --force.

Example: author asks for a JSONC section

inject:
  - into: "config/app.jsonc"
    region: "features"
    content: |
      "analytics_enabled": true,
      "analytics_sample_rate": 0.1

JSONC accepts comments, so Toha can use visible markers. The rest of the file remains owned by the operator.

Second apply changes no bytes. An edit between the markers produces a conflict instead of a silent overwrite.

Strict JSON needs a decision

Strict JSON has no comments, so the visible-marker approach cannot produce a valid .json file.

  • Proposed behavior: refuse marker injection during planning.
  • Message names alternatives: use JSONC/JSON5, let Toha manage the whole file, or use structured editing if that option is approved.
  • Existing behavior: whole-file JSON rendering continues to work.

This is a proposed boundary for the new injection feature. It is not approved yet.

Structured editing: author request

Structured editing changes one value by its JSON path. It works with strict JSON and does not need marker comments.

inject:
  - into: "package.json"
    struct:
      path: "scripts.build"
      value: "tsc"

This author surface and its timing are options under D6b. They are not approved scope.

Structured editing: target before and after

  • BEFORE
    {
  "name": "sample-app",
  "scripts": {
    "start": "node index.js"
  }
}
  • AFTER
    {
  "name": "sample-app",
  "scripts": {
    "start": "node index.js",
    "build": "tsc"
  }
}

Ownership: Toha owns the value at scripts.build and sets it back to the requested value on later runs.

The recommended editor changes only the necessary range. In JSONC it also preserves nearby comments, spacing, and trailing commas.

What stays outside this design

  • Combining both the human and generated edits through a three-way merge.
  • A separate toha inject command or a second apply pass.
  • Automatic formatting of injected content.
  • Changes to the interview engine or existing whole-file conflict rules.
  • Canonical specification, schema, and guide edits; the paired implementation owns them after approval.

Pending choice: structured value editing is not silently excluded. D6b keeps “build now” and “fast-follow” as live options.

What reviewers should attack

  • Safe repeat: can any normal replay duplicate or rewrite an unchanged section?
  • Ownership: can Toha alter bytes outside its named section?
  • Conflict handling: can --force create a missing section or overwrite unrelated text?
  • Order: if Toha creates a file and injects into it in one plan, does injection read the newly created content?
  • Safety rules: do existing target-path, symbolic-link, and .git checks run before every read and write?
  • JSON fidelity: does the chosen method preserve what it claims to preserve?

Three ways to change an existing file

ApproachGood atTradeoff

Recommendation: visible sections as the base. If structured editing is approved, use a format-preserving editor. Do not use a whole-document rewrite for user-owned files.

Real tools: managed sections

  • Ansible blockinfile finds a marked block, removes it, inserts the new block, and writes only when bytes differ. This is the closest mature precedent.
  • Ansible lineinfile uses a regular expression for one line; safe repeat depends more on the author.
  • scaffold inserts at a line but has no repeat guard, so another run inserts again.

Source evidence: Ansible 7ec731b blockinfile.py:334-367 and lineinfile.py:295-479; scaffold 475e9bc injector.go:27-82.

Real tools: format-preserving editors

  • jsonc-parser for Rust keeps comments and whitespace in a concrete syntax tree, then changes one node. This is the recommended structured mechanism if D6b is approved.
  • VS Code's node-jsonc-parser returns minimal offset/length/content edits. It is the TypeScript version of the same approach.
  • toml_edit stores formatting on each node. It is the mature TOML analogue.

Source evidence: jsonc-parser c7d4cf5 cst/mod.rs:1-5,1356; node-jsonc-parser dba4356 edit.ts:15-140; toml_edit e4b8bda repr.rs:187.

Real tools: whole-document rewrite

  • jaq is a capable query engine, but it drops comments while reading and prints a new document. Recommend against it for this feature.
  • serde_json has no comment model; preserving key order does not preserve the original bytes.
  • json5-rs accepts comments as input but does not retain them in an editable document model.
  • npm package-json rewrites the full document while carrying forward detected indentation and newline style.

Source evidence: jaq f167ad4 read.rs:10-19, write.rs:202-260; serde_json afdf6fc; json5-rs fd55f90; npm package-json a7dafdb.

Real tools: regenerate and merge

  • Copier and Cruft render the old and new template versions, compute a difference, then use Git-style merge tools.
  • This approach handles broad template updates, but it is a better fit for Toha's separate project-update work than for one bounded section.

Source evidence: Copier 01c6832 and Cruft 33f6b72. Full revision, file, and symbol notes remain in the design package.

Decisions 1–3: the author experience

D1 — Show ownership markers in the target file

A. Write visible comments. Recommend A so that people can see the boundary.
B. Hide ownership elsewhere.

D2 — Name the template setting inject

A. Use the top-level list shown in the examples. Recommend A so that one setting describes all managed sections.
B. Put injection under existing whole-file output.

D3 — Choose comment style from the file type

A. Infer known types, allow an override, and reject unknown types without one. Recommend A so that Toha never guesses silently.
B. Require every author to specify it.

Decisions 4, 5, 7, 8: safety defaults

D4 — Human edit inside the section: A. stop; --force replaces only that section. Recommend A. B. always overwrite.

D5 — Missing target: A. require create: true. Recommend A so that a spelling error cannot create a surprise file. B. create by default.

D7 — Write method: A. complete temporary file, then atomic rename. Recommend A so that interruption cannot leave half a file. B. edit in place.

D8 — Region fingerprint: A. reuse the existing sha2 library. Recommend A so that no new dependency is needed. B. add another checksum.

Decision 6a: JSON through visible markers

A. JSONC and JSON5 use comment markers; strict JSON marker injection is refused during planning.

Existing whole-file JSON rendering remains available. The error names JSONC/JSON5, whole-file output, and structured editing as alternatives.

Recommend A so that Toha never writes invalid JSON.

B. Do not support JSON-family marker injection.

This is a proposed boundary for the new feature. Bob's decision is required.

Decision 6b: when to add structured JSON editing

The sequencing options below assume the recommended jsonc-parser mechanism and the “Toha owns this value at this path” rule. D9 separately decides the mechanism.

A. Fast-follow after 0.2.0. Reserve the struct: shape now; build visible sections first. Recommend A so that the base feature stays medium-sized.

B. Build it in the paired implementation now. Deliver strict-JSON value editing with the first injection release.

These are co-equal choices. The paired implementation is not narrowed until Bob decides.

Decision 9: use jaq for structured editing?

A. Use jaq. Gain a powerful query language, but rewrite the whole document and lose comments and original formatting.

B. Use jsonc-parser if structured editing is approved. Change one value while preserving unrelated source text.

Recommend B so that a change to one owned value does not rewrite the user's file.

This is a recommendation from source evidence and the design comparison. It is not a settled decision.

Expected build size

Visible-section base: medium; about one to two focused agent sessions.

  • Template parsing and validation.
  • One pure region resolver.
  • One ordered apply stage.
  • Dry-run and error reporting.
  • Specifications, schema, guide, and end-to-end fixtures.

If D6b chooses “build now”: add the structured editor integration and its JSON/JSONC preservation fixtures to that estimate.

Where the complexity sits

The base design concentrates the difficult rules in one pure resolver: find or place the section, compare its fingerprint, and return either no change, a complete new file, or a clear error.

  • Moderate: byte preservation, comment-style selection, and ordering with whole-file writes.
  • Contained: interview behavior and existing whole-file generation stay unchanged.
  • Optional extra: structured editing adds a dependency and a second ownership rule, but uses the same plan-before-write flow.
