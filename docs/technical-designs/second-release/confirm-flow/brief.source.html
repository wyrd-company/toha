Toha 0.2.0 · Design brief · Phase C

A confirm answer can steer the run

Let a template say "if they answer this way, stop — or preview — or skip the rest," while a plain yes/no question keeps working exactly as it does today.

Approved design sought design only paired build: task 1062

Task

A confirm question today only produces a yes/no value that later questions can read. This design lets a template bind a specific answer to an action that steers the run itself.

  • Stop — end the run now; write no files, run no hooks.
  • Dry-run — finish the questions, show the plan, write nothing.
  • Skip — skip the rest of the questions (the whole run, or just the current group).

Actions are written in the template as data, never guessed from the wording of the prompt. A confirm with no action is unchanged. The same behavior works from every way Toha is driven: the terminal, an answers file, a saved (staged) interview, a direct apply, and the library.

Depends on: the presets/configured-defaults work (already merged) and the error-attribution design (approved). Paired implementation: task 1062. Repository: github.com/wyrd-company/toha.

Pre-mortem — imagine the build failed. Why?

  • A "stop" still wrote something. A file or a hook slipped through because "don't apply" was left to each caller to remember.
  • Answering "no, stop" errored out. The stop ran the leftover questions anyway and tripped over a bad default in one the user never saw.
  • A plain yes/no question changed. Adding actions quietly altered how ordinary confirms behave.
  • The action was guessed from the prompt text instead of being declared, so it fired in surprising places.
  • Resuming a saved interview behaved differently because the action was stored as extra state that drifted from the answers.
  • A rejected answers file still triggered an action or left a half-saved interview.

The design closes each of these by construction; see Reviewer focus.

Module and seam

template.yml (action: on a confirm)
      │  load-time checks: action only on confirm; not empty;
      │  known values only; "skip: group" needs a group
      ▼
  interview engine ── reaches an ANSWERED, ACTIVE confirm
      │            └─► ONE decision point reads the answer + the declared action
      │                 stop   → end the interview (a result that cannot be applied)
      │                 dry-run→ finish, but mark "plan only"
      │                 skip   → skip the rest (reuses the existing skip machinery)
      ▼
  interview result ── Asking · Complete(plan-or-preview) · Ended(stopped)
      │
      ├─ terminal    ─┐
      ├─ answers file ─┤ thin adapters: each just routes the result;
      ├─ saved/staged ─┤ none re-implements the stop/preview/skip rules
      ├─ direct apply ─┤
      └─ library      ─┘
             │
   proceed → build plan → APPLY (the only place files are written / hooks run)
   preview → build plan → SHOW, do not apply
   stopped → nothing to build; cannot apply

The engine owns the decision in one place. Everything downstream only reads the outcome. "No files, no hooks" on stop/preview means simply not reaching the one apply step.

Public interfaces

Navigate down for each surface. Signatures are the contract the build fills in.

The result the engine returns

pub enum Interview<'a> {
    Asking(Pending<'a>),
    Complete(Completed),   // now also says: apply, or preview only
    Ended(Ended),          // NEW: a confirm "stop" ended the run
}

"Stopped" is its own result that carries nothing to apply — so there is no way, in code, to write files from a stopped run.

A one-call gate for library and direct callers

// Build unless stopped; apply only when proceeding. One place, one policy.
pub fn realize(template, outcome, target, options, runner)
    -> Result<Realized, RealizeError>;

pub enum Realized {
    Stopped { by: Id },              // nothing built, nothing written
    Previewed { plan: Plan, by: Id },// dry-run: plan built, shown, not applied
    Applied(Applied),                // normal apply
}

The drivers, unchanged in spirit

// terminal: returns the outcome instead of only a completion

Data structures

Navigate down for each shape.

How a template declares an action

- id: proceed
  type: confirm
  prompt: "Ready to scaffold?"
  action:
    when_false: { skip: rest }   # "no" skips the remaining questions
- id: overwrite_ok
  type: confirm
  prompt: "Target is not empty. Continue anyway?"
  action:
    when_false: stop             # "no" ends the run
- id: preview_first
  type: confirm
  prompt: "Show the plan first?"
  action:
    when_true: dry-run           # "yes" previews, writes nothing

Values: stop, dry-run, or { skip: rest | group }. At least one of when_true/when_false.

What the engine carries

enum Disposition { Proceed, DryRun }   // on a completed interview

struct Ended {                          // a stopped interview
    by: Id,                             // the confirm that stopped it
    answers: Answers,                   // gathered so far, for reporting only
    messages: Vec<String>,             // no hooks, no plannable value
}

Nothing new is saved to disk. The stop/preview decision is recomputed from the recorded answers every time, so resuming a saved interview reproduces it exactly.

On the wire (for agents and scripts)

{ "protocol": 1, "status": "stopped",
  "context": { "target": "/abs/out", "template": "web-service", "commit": null },
  "by": "overwrite_ok", "answers": { "overwrite_ok": false }, "messages": [] }

A new stopped status, and an optional "dry-run" marker on a completion. Both are additive; an ordinary completion looks exactly as it does today.

Behaviors to prove

Each is written so it can fail. Navigate down for the groups.

The safety guarantees

ClaimHow it could fail
A plain confirm is unchangedSame answers and output as today, byte for byte, on every driver
Stop writes nothing, runs no hookCheck the target folder is untouched and the hook recorder is empty
Stop can't fault on a later questionA template with a bad default after the stop still stops cleanly
Preview writes nothingPlan is shown; target folder and hook recorder stay empty

Scope, resume, and rejection

ClaimHow it could fail
"skip: group" stays inside its groupQuestions after the group are still asked; nested groups compose
Skipped questions get defined valuesEach records its normal default/empty and the existing "answer not used" warning
Resuming reproduces the outcomeReplaying the saved answers yields the identical stop/preview/skip
A rejected answers file does nothingNo action fires and no interview is saved when any answer is rejected
Only the declared answer firesThe other yes/no value proceeds normally

Same result everywhere

The same template and answers produce the same outcome through the terminal, an answers file, a saved interview, a direct apply, and the library — and the machine-readable "stopped" document is identical between the answers-file and saved-interview paths.

Out of scope

  • The existing question/skip/default rules underneath the decision point — reused, not changed.
  • Preset selection and error-attribution internals — owned by their own designs.
  • Any new trust, permission, timeout, version-pin, or external-process behavior. A confirm action never runs a hook or touches trust.
  • Actions on non-confirm questions; guessing actions from prompt text; chained or per-run overridden actions.

Reviewer focus — what to attack

  • Can any path write a file or run a hook on stop or preview? The claim is "no, by construction."
  • Does a rejected answers file ever fire an action or half-save? The claim is "never."
  • Does a resumed interview ever differ from a fresh one? The claim is "identical, because nothing extra is stored."
  • Does an ordinary confirm change at all? The claim is "not one byte."
  • Does "skip" ever leave a question with an undefined value? The claim is "it reuses the existing skip values."

Alternatives explored

Four independent designs were produced and cross-judged; the base was chosen and the best ideas grafted in.

  • Chosen: the decision is an effect the engine emits where the answer is read; a stop is a result that cannot be applied.
  • Also strong (grafted): a one-call "realize" gate so library and direct callers never re-implement the rules — folded in.
  • Rejected: modelling "stop" as "silently skip everything and finish." It made a stop do needless work and could error on a question the user never reached, and reported the run as "complete."
  • Rejected: guessing the action from the prompt, or a separate scanner that re-derives the interview — both invite drift.

No decision adds a permission, access, timeout, version-pin, or external-process behavior. The feature is additive and opt-in; ordinary confirms are unchanged.

Size

Medium. One decision point and one new result in the engine; small routing changes in each driver; the template loader gains the action and its four load-time checks; the documented spec/guide edits are owned by the paired build (task 1062); plus the behavior tests above.

Expected implementation time: one to two focused agent days after refreshing onto the current base.

Complexity

Low to moderate. Skip reuses machinery that already exists; nothing new is saved to disk; there is no new concurrency, no new dependency, and no new external behavior. The main care is keeping the decision in one place and proving the "writes nothing on stop/preview" guarantee.
