Toha 0.2.0 · Design brief · approved 2026-09-28

Steering the interview with a flow node

Control moves off the confirm question and into a small new flow node that fires an action — stop, abort (stop and discard the saved interview), preview, or skip — when a condition is true. Ordinary yes/no questions are untouched.

Approved design only paired build: task 1062

Task

You asked: instead of attaching an action to a confirm question, use a new flow block with a when condition and an action. This brief does exactly that and compares it to the earlier confirm-based shape.

  • Stop — end the run now; write no files, run no hooks.
  • Abort — stop and also discard the saved (staged) interview for this target.
  • Dry-run — finish the questions, show the plan, write nothing.
  • Skip — skip the rest of the interview, or the rest of the current group.

The flow node reads the same when conditions questions already use, so it can trigger on any answer (or combination), not just one yes/no. The confirm question type is not changed at all, so ordinary confirms are identical to today. Actions are written in the template as data, never guessed from the prompt wording. Depends on the presets work (merged) and the error-attribution design (approved); paired build is task 1062. Repository: github.com/wyrd-company/toha.

Pre-mortem — imagine the build failed. Why?

  • A "stop" still wrote something. A file or hook slipped through because "don't apply" was left to each caller to remember.
  • Answering "no, stop" errored out. The stop ran leftover questions and tripped over a bad default in one the user never saw.
  • An ordinary yes/no question changed. Adding control quietly altered plain confirms.
  • The action was guessed from the prompt instead of being declared.
  • Resuming behaved differently because the decision was stored as extra state that drifted from the answers.
  • A rejected answers file still triggered an action or left a half-saved interview.

The design closes each of these by construction; see Reviewer focus.

Module and seam

template.yml   a `flow` node in the interview list: when + action
      │  load-time checks: known action only; "skip: group" needs a group
      ▼
  interview engine  reaches the flow node, evaluates its `when`
      │            └─► ONE place decides: stop / dry-run / skip
      │                 (a peer of the existing message/hook nodes; reuses `when`)
      ▼
  interview result  Asking · Complete(plan or preview) · Ended(stopped)
      │
      ├─ terminal · answers-file · saved/staged · direct · library
      │      thin routers: each reads the result; none re-implements the rules
      ▼
   proceed → build plan → APPLY  (the only place files are written / hooks run)
   preview → build plan → SHOW, do not apply
   stopped → nothing to build; cannot apply

The confirm type is not touched. "No files, no hooks" on stop/preview means simply not reaching the one apply step; a stop is a result that literally cannot be planned.

Public interfaces

Navigate down for each surface.

The result the engine returns

pub enum Interview<'a> {
    Asking(Pending<'a>),
    Complete(Completed),   // says: apply, or preview only
    Ended(Ended),          // NEW: a flow `stop` ended the run — cannot be planned
}

A stopped run carries nothing to apply, so no code can write files from it.

One seam for proceed-vs-preview

match completed.step() {
    Step::Plan { apply } => {
        let plan = Plan::build(&template, &completed, target)?; // pure, safe
        if apply { plan.apply(target, opts, &runner)?; }        // proceed
        else { show(&plan); }                                   // dry-run
    }
}

Every driver routes through this one method; the CLI --dry-run just forces apply off.

Data structures

Navigate down for each shape.

How a template writes a flow node

interview:
  - id: proceed
    type: confirm                 # ORDINARY confirm — unchanged
    prompt: "Ready to scaffold?"
  - flow: stop                    # the action is the value of `flow:`
    when: "not proceed"           # the existing `when`, as a sibling
    label: "declined at proceed gate"

  - flow: abort                   # stop AND discard the saved interview
    when: "cancel"

  - flow: dry-run
    when: "mode == 'preview'"     # any expression, not just one confirm

  - group: telemetry
    nodes:
      - id: configure_now
        type: confirm
        prompt: "Configure telemetry now?"
      - flow: { skip: group }     # skip the REST of this group from here
        when: "not configure_now"

Actions: stop, abort, dry-run, { skip: rest }, { skip: group }. abort stops and removes the saved interview. when is optional (a flow with no when always fires).

What the engine carries

enum Disposition { Proceed, DryRun }   // on a completed interview

struct Ended {                          // a stopped interview
    messages: Vec<String>,             // reached so far, for reporting
    label: Option<String>,             // no plannable value, no hooks
}

Nothing new is saved to disk. The decision is recomputed from the recorded answers every time, so resuming a saved interview reproduces it exactly.

On the wire (for agents and scripts)

{ "protocol": 1, "status": "ended",
  "context": { "target": "/abs/out", "template": "web-service", "commit": null },
  "messages": ["Stopping: nothing was written."], "label": "declined at proceed gate" }

A new ended status, plus an optional "dry-run" marker on a completion. Both additive; an ordinary completion looks exactly as today.

Behaviors to prove

Each is written so it can fail. Navigate down for the groups.

The safety guarantees

ClaimHow it could fail
An ordinary confirm is unchangedSame answers and output as today, byte for byte, on every driver
Stop writes nothing, runs no hookTarget folder untouched and the hook recorder empty
Stop can't fault on a later questionA template with a bad default after the stop still stops cleanly
Preview writes nothingPlan is shown; target folder and hook recorder stay empty

Scope, resume, and rejection

ClaimHow it could fail
"skip: group" skips the rest of its groupQuestions after the group are still asked; nested groups compose
Skipped questions get defined valuesEach records its normal default/empty and the existing "answer not used" warning
A flow fires only when reached and trueA flow under a false condition or a skipped group never fires
Resuming reproduces the outcomeReplaying the saved answers yields the identical stop/preview/skip
A rejected answers file does nothingNo action fires and no interview is saved when any answer is rejected

Same result everywhere

The same template and answers produce the same outcome through the terminal, an answers file, a saved interview, a direct apply, and the library — and the machine-readable "ended" document is identical between the answers-file and saved-interview paths.

Out of scope

  • The existing question/skip/default rules underneath the flow decision — reused, not changed.
  • Preset selection and error-attribution internals — owned by their own designs.
  • Any new trust, permission, timeout, version-pin, or external-process behavior. A flow action never runs a hook or touches trust.
  • Changing the confirm type; guessing actions from prompt text; chained or per-run overridden actions.

Reviewer focus — what to attack

  • Can any path write a file or run a hook on stop or preview? Claim: "no, by construction."
  • Does a rejected answers file ever fire an action or half-save? Claim: "never."
  • Does a resumed interview ever differ from a fresh one? Claim: "identical; nothing extra stored."
  • Does an ordinary confirm change at all? Claim: "not one byte — the confirm type is untouched."
  • Does "skip" ever leave a question with an undefined value? Claim: "it reuses the existing skip values."

Alternatives explored — flow node vs the earlier confirm-action shape

Two rounds of independent, cross-judged designs. Your 19:06 note prompted a fresh round for the flow-node shape.

 flow node (recommended)action on confirm (round 1)
Changes the confirm typeNo — ordinary confirms untouchedYes — adds a guarded field
TriggerAny condition over prior answersOne confirm's yes/no
Expressiveness"stop when X and Y" reads naturallyBound to one question
Simplest "no → stop"One line away from the questionReads on the question itself

Both the internal reviewer and an independent other-model reviewer recommend the flow node: it reuses machinery Toha already has, leaves ordinary confirms untouched, and is far more expressive. Its one cost is that the trigger sits one line from the question for the simplest case. The earlier confirm-action design is preserved for comparison.

Merge order is already set (not a decision): the build for this design lands after the error-attribution build. Design preparation is independent; runtime integration is not.

No decision adds a permission, access, timeout, version-pin, or external-process behavior. The feature is additive and opt-in; ordinary confirms are unchanged.

Size

Medium. A new flow node kind mirroring the existing message/hook nodes; one decision point and one new result in the engine; small routing changes in each driver; the documented spec/guide edits are owned by the paired build (task 1062); plus the behavior tests above.

Expected implementation time: one to two focused agent days after refreshing onto the current base.

Complexity

Low to moderate. The flow node reuses the existing when, node-walk, and skip machinery; nothing new is saved to disk; there is no new concurrency, no new dependency, and no new external behavior. The main care is keeping the decision in one place and proving the "writes nothing on stop/preview" guarantee.
