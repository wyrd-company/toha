Toha 0.2.0 · Design brief · Phase C checkpoint

One Jinja context from interview to plan

Templates receive exact target, identity, host, execution, and five trust-gated values through one replay-stable snapshot.

role: architect paired implementation: 1060 BOB DECISION REQUIRED design only

Prepared from five blind candidates, independent scoring, and the integrated configured-default and hook-review contracts. No runtime or shared contract was edited.

Task

Define Toha-owned Jinja variables once, then make terminal, headless, staged/resumed, and direct crate callers observe the same typed context.

What templates get

  • Canonical target basename
  • Short name, formal name, aliases, source
  • OS, architecture, Linux distribution facts
  • Admin and originating interactive status
  • Five optional values behind trust

Success

  • One pure interview engine
  • One projection for interview and planning
  • Deterministic staged replay
  • No whole-environment access
  • No second target normalizer

Toha repository · 0.2.0 release pull request

Pre-mortem — the build failed. Why?

  • Interview and generated files disagree. The context was rebuilt twice. One snapshot and one projection remove the second policy.
  • A resumed interview changes branches. Host or environment values were re-read. Staging stores the original snapshot.
  • Revoked trust still exposes stored values. Replay skipped the live gate. Current access is required before any replay.
  • A context name silently shadows template data. Merge order became policy. Exact collisions fail at template load.
  • Config presets become a second Jinja namespace. Presets still flatten only into question defaults.
  • Target spellings disagree. Planning used the raw CLI path. The existing canonical result is used end to end.

Out of scope

  • Runtime, specification, schema, or guide edits in this design task.
  • Arbitrary environment access or a dynamic lookup function.
  • Trust commands or a changed review digest.
  • A second target normalizer or dependency on the target-fix implementation.
  • Configured-default behavior, origin, or presets naming changes.
  • A new Run façade, staged encryption, or file-permission policy.
  • Timeouts, pinned-version checks, or application subprocesses.

Reviewer focus

  • Hidden process read: find any engine, Jinja, plan, or staging path that reads ambient state.
  • Trust bypass: replay a granted record after approval changes, or expose a sixth value.
  • Dual context: make an interview field and plan field observe different facts.
  • Collision hole: shadow a reserved name through data, question, computed, or each.
  • Predecessor drift: merge presets into Jinja, replace the trust evaluator, or normalize a target twice.
  • Unsupported restriction: break root, non-Unicode, terminal continuation, headless, staged, or crate use.
  • Leakage: place a granted value in debug output, an error, or protocol metadata.

Alternatives explored — policy and lifetime

  • MiniJinja globals: rejected — hidden process state and broken replay.
  • Plan-only context: rejected — interview expressions remain incomplete.
  • Re-read on resume: rejected — old branches can change.
  • Stored grant without reauthorization: rejected — revocation has no effect.
  • Separate environment permission: rejected — outside the requested --trust gate.
  • Reserve all toha_ names: rejected — unrequested compatibility restriction.

Decision needed first — environment grant

A — effective template trust

--trust or a current matching reviewed-registry approval grants the five values.

RECOMMENDED

One content-bound trust decision for the invocation. Folder, direct Git, local-registry, and bundled selections still require --trust.

B — --trust only

Registry approval continues to authorize hooks, but never the five values.

NARROWER

Separates permissions, but reviewed templates require another explicit action every time they need these values.

Access semantics included in the recommendation

  • Add existing --trust spelling to stage and continue.
  • Capture only user, hostname, editor, shell, and visual after access.
  • Persist at most those five values in plaintext in existing staged state.
  • Require current effective access before replay of a granted snapshot.
  • Repeat --trust to resume a stage first granted for one run.
  • Never elevate a saved denial; start a new interview to change the snapshot.
