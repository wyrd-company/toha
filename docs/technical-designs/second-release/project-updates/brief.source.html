Toha 0.2.0 · Design checkpoint · revision 3

Keep generated projects up to date

Every apply saves a snapshot of what it wrote. Later, an apply from that snapshot merges the template's new version into the project the way git merge would.

design only 4 decisions need approval 4 disclosures need approval

Task

Let a project made from a template take the template's later versions without losing its owner's edits, using git and the owner's own git habits.

Today

  • Apply writes files and remembers nothing.
  • A newer template can only overwrite the project (--force).

With this design

  • Every apply in a clean git target saves a snapshot.
  • toha apply TEMPLATE PATH --from SNAPSHOT merges the new version in.
  • Conflicts look exactly like a git merge conflict.

Acceptance scenario (agreed)

  1. An operator applies version A in a clean git repo and commits; Toha reports snapshot S1; they push the branch and S1.
  2. They edit README.md on lines version B also changes.
  3. A teammate clones, runs toha init, fetches; toha snapshots list marks S1 as the likely base.
  4. toha apply …@B . --from S1: src/app.txt updated, src/health.txt added, README.md conflicted (git status shows UU); new snapshot S2.
  5. They resolve, commit, push S2. The same command from S2 says "already at B" and changes nothing.

How an update works

Snapshots live under refs/toha/snapshots/<id>: parentless commits, not branches, invisible in the project's history.

Commands

CommandWhat it does
apply T PAs today; also saves a snapshot when the git target was clean
apply T P --from IDUpdate from snapshot ID; asks only new questions; --reanswer revisits all

snapshots cleanPick snapshots to remove; --keep N; JSON for agents
initAdds the git fetch setting so clones receive snapshots

Toha never commits, pushes, fetches, or runs git init. It prints the git push line for each snapshot.

Decisions needed first

  1. Owned content merges by line. An injected region or JSON value merges like the rest of the file: overlapping edits conflict, separate edits both apply. Recommended. Alternative: Toha's value always wins, silently.
  2. Dates stay put. Every render uses the date of the first snapshot, so a rendered date does not change at each update. Recommended.
  3. No git drivers. Toha never runs git merge or filter programs (for example git-lfs); such paths are reported as conflicts and left as the operator has them. Recommended. Alternative: run them as git does, which starts external programs.
  4. Hook files carried forward. A file a hook rewrote unchanged is kept, not deleted. Cost: a file a hook stops making is never removed by an update. Recommended.

Disclosures (each needs explicit approval)

  • New effect on apply: every apply in a clean git target writes git objects and one ref under refs/toha/snapshots/. No branch, index, HEAD, or remote is touched.
  • New effect on update: --from and --baseline write the git index (merged entries and conflict stages), as git merge does.
  • Git config: toha init, when run, adds one fetch setting to the repo's local config.
  • Dependency: two more features of the existing gix 0.87.1 (merge, status), adding gix-merge, gix-imara-diff, gix-status, gix-dir from gitoxide.
  • No new permission, timeout, pinned-version check, or subprocess. No capability is removed.

Already decided with Bob

  • Git required for updates; no update command; the user picks the base snapshot.
  • No upgrade/downgrade labels; clean target required; Toha never commits.
  • Hooks run only in a throwaway checkout; non-file hook effects are not Toha's concern.
  • Snapshots are parentless with stable time-ordered ids; the user shares them with git.
  • All three caller routes; monorepo targets scoped to their directory.

Pre-mortem: why this could fail

  • An operator edit is lost. Guarded by git merge rules, index conflict stages, a re-check under the index lock, rollback, and never deleting a file Toha only edits inside.
  • Wrong base. The user picks it; Toha marks the likely one and refuses a snapshot of another template or directory.
  • Teammates never get snapshots. Refs are not fetched by default; toha init and printed push lines make it one step each.
  • gitoxide cannot do a step in process. The spike proved every step; removing git drivers in memory is the one unproven point and the first implementation check.
  • Replaying answers breaks on a changed interview. A dedicated replay adapter handles new, removed, rejected, and looped questions.

Data structures: what a snapshot captures

  • toha: every file the plan owns, even if unchanged.
  • edit: files Toha edits inside, with the regions and JSON values it owns; a dropped injection is removed inside the file, and a file that no longer owns anything is released to the operator, never deleted.
  • hook: files hooks created or changed; carried forward when a hook rewrites them unchanged.
  • Left out: untracked ignored files, submodules, changes outside the target.
  • Symbolic links kept as links; executable bit kept; line endings stored as git add would.

A fetched snapshot is checked before use: no parent, only snapshot.json and files/, valid schema, paths match.

Out of scope

  • Rename detection and moving a target directory.
  • Upgrade/downgrade labels (version ordering).
  • Pushing, fetching, pruning, committing, git init.
  • Onboarding in toha init (backlog task 1108).
  • Hook effects that are not committed files.
  • Honouring git merge and filter drivers.
  • Changes to injection's apply-time rules, the answers-document contract, hook results, or trust.

Reviewer focus

  • Any path where an operator edit is lost without a conflict (retraction, capture rules, occupied paths, rollback).
  • The index write: stages, cached tree, lock, and re-check.
  • The update replay adapter against the unchanged interview engine.
  • The in-memory driver removal at every gitoxide entry point.
  • The snapshot boundary against a forged ref from a teammate.

A read-only reviewer from another model family reviewed this design twice: 14 findings, then 4 more on the fixes (3 blockers in all). All are addressed in this revision.

Size and complexity

Size: XL

About 4–6 focused agent days: the snapshot module, replay adapter, two crate-private seams, three commands, spec and schema updates, and a two-clone fixture harness.

Complexity: high, with this plan

The risky parts are proven by the spike (tree merge, index stages, refs, checkout). The remaining risk is breadth: many edge cases, each with a named fixture.
