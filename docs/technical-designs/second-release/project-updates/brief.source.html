Toha 0.2.0 · Design checkpoint

Keep generated projects up to date

When a template improves, a project made from it can take the improvement without losing the changes its owner made.

design only 9 decisions need approval 1 capability restriction disclosed

Task

Design toha update: bring a generated project from template version A to version B, keep the owner's edits, and show a clear conflict when both changed the same lines.

Today

  • Toha writes files and forgets.
  • Nothing in the project says which template or answers made it.
  • The only way to take a template change is --force, which overwrites every edit.

Designed

  • Every apply leaves a small record in the project.
  • toha update redoes the template at the new version with the same answers.
  • It merges line by line, the way git merges branches.

How the merge works

For every file Toha made, it compares three versions:

VersionWhere it comes from
Base: what Toha wrote last timeThe template at version A, with the recorded answers
Yours: the file nowThe project on disk, with the owner's edits
New: what Toha would write nowThe template at version B, with the same answers
  • Only the template changed: take the new version.
  • Only you changed it: keep yours.
  • Both changed different lines: combine both.
  • Both changed the same lines: conflict. Nothing is written unless you ask for conflict markers.

Walkthrough: the record

Project before this design

sample-service/
├── README.md
├── config/app.toml
└── src/app.txt

Project after an apply

sample-service/
├── .toha/applied/
│   └── receipt-5e1d0c7a.json
├── README.md
├── config/app.toml
└── src/app.txt

The record is committed with the project, so it survives clone, copy, and move. There is one small file per template used in the project.

Walkthrough: preview an update

$ toha update ./sample-service --dry-run
receipt: 3f9a1c2 -> 8be0d41
update   src/app.txt        (whole)                # template changed, you did not
merge    README.md          (whole)                # both changed, lines combine
update   config/app.toml    (region features)      # the template's block changed
converge package.json       (value scripts.build)  # value set back to the template's
add      src/health.txt     (whole)                # new in the template
retract  docs/legacy.md     (whole)                # dropped, you never edited it
release  notes/todo.md      (whole)                # dropped, you edited it: now yours
conflict src/routes.txt     (whole, 2 hunks)       # both changed the same lines

Text after # explains each line; it is not part of the output.

Toha never deletes a file its owner edited.

Walkthrough: a conflict

Default: nothing written

$ toha update ./sample-service
conflicting changes, nothing written:
  src/routes.txt (whole, 2 hunks)
to write git-style conflict markers:
  toha update --on-conflict markers ./sample-service

With markers: resolve by hand

<<<<<<< operator
route /orders  -> handler_v2
||||||| toha 3f9a1c2
route /orders  -> handler
=======
route /orders  -> orders_handler
>>>>>>> toha 8be0d41

The next update refuses while markers remain, so unresolved markers are never merged in as content.

Three kinds of ownership, three rules

Toha ownsExampleOn update
A whole filesrc/app.txtLine-by-line merge with your edits
A marked region in your filea block in config/app.tomlMerge inside the region only. Text outside the markers is never touched.
One value in a JSON filescripts.build in package.jsonSet to the template's value, as injection already does. The rest of the file is untouched.

These rules come from the approved content-injection design. Update keeps them; it does not treat a region or a JSON value as a whole file.

Region example

Before update

[application]
# >>> toha:region features >>>
analytics_enabled = true
# <<< toha:end features sha256:a7f3… <<<
name = "sample-service"

After update (template adds a line)

[application]
# >>> toha:region features >>>
analytics_enabled = true
analytics_sample_rate = 0.1
# <<< toha:end features sha256:5c02… <<<
name = "sample-service"

The owner's name line outside the markers stays as it is.

When the template drops something

Dropped itemOwner did not edit itOwner edited it
Whole fileDeletedKept; Toha stops owning it
RegionMarkers and text removedMarkers removed, text kept
JSON valueKey removedValue kept

A deletion needs proof that Toha really wrote that content, so an edited or forged record can never cause data loss.

Projects made before this feature

No record: update refuses

$ toha update ./old-service
./old-service has no applied record
to adopt it: toha adopt TEMPLATE ./old-service

Adopt once, then update

$ toha adopt forge:catalog/receipt@stable \
    ./old-service --at 3f9a1c2
? Label: Sample
matches  src/app.txt
differs  README.md
recorded .toha/applied/receipt-5e1d0c7a.json

Adopt asks the questions again and writes only the record. It never changes the project's files. Differences count as the owner's edits.

Pre-mortem: why this could fail

FailureWhat prevents it
Answers replay differently, so the old version cannot be rebuiltRecord the raw answers exactly as staging does; drop answers for removed questions; freeze the time value
A bad record deletes the owner's filesDelete only when the rebuilt old version proves Toha wrote it
The old template version is gone upstreamSafe mode: detect edits, never delete, refuse unclear merges
A crash leaves files new but the record oldRecord written last; rerunning finishes the job
Dates in files change on every updateThe first apply's time is reused
The merge library starts another programOnly the built-in text merge function is called; a test fails if a process starts

Module and seam

New: the project module, and gitoxide's merge feature. Everything else is reused unchanged. A command reaches a written file through three source files.

Data structures: the record file

{
  "template": "forge:catalog/receipt@stable",
  "commit": "3f9a1c2e8d7b…c5b4a39",
  "generated": "2026-03-14T09:26:53+00:00[UTC]",
  "submissions": [
    { "label": "Sample", "quantity": 4 },
    { "use_vcs": true }
  ],
  "owned": {
    "files":   { "README.md": "sha256:9c1e…" },
    "regions": { "config/app.toml": ["features"] },
    "values":  { "package.json":
                 { "scripts.build": "sha256:77f2…" } }
  }
}
  • template, commit: which template and exact version
  • generated: the time of the first apply, reused so dates stay stable
  • submissions: the answers as typed, before formatting
  • owned: what Toha owns, with fingerprints to detect edits

Not stored: file contents, the project's path, hook output, trust, user name, or host name.

Out of scope

  • Detecting renamed files (a move is a remove plus an add).
  • Searching project history to guess which version made an old project.
  • Changing the approved rules for injection, answers files, hook results, staged interviews, or trust.
  • Toha making commits, tags, or notes in the owner's git repository.
  • Letting a question keep its answer out of the record.
  • New permissions, timeouts, version checks, or starting other programs.

Reviewer focus

  1. No path can delete an owner-edited file, even with a forged record.
  2. Replay reproduces the original answers: raw values, removed questions filtered, frozen time.
  3. Region and JSON value keep the approved injection rules.
  4. The record is written last, and a rerun after any failure converges.
  5. The merge never starts another program.
  6. Staged interviews are never read or changed by update or adopt.

Alternatives explored: the merge base

Rebuild the old version chosen

  • Record stays small and readable
  • One source of truth: the template
  • Needs the old version; safe mode without it

Store every written file in the record

  • Full merges even offline
  • Large record; a second copy of every file
  • Answer-derived content committed twice

Two independent designs explored these two shapes; a separate judge scored both.

Disclosures for separate approval

Capability restriction. Today a template may write any path outside .git. With decision 2, a template that writes into .toha/applied/ fails before anything is written.
New effect. Every toha apply adds .toha/applied/<name>.json to the project (decision 8).
New dependency code. gitoxide's merge feature adds the gix-merge crate (decision 3). It can run external merge drivers; Toha never calls that part, and a test enforces it.

No new permission, timeout, version check, or application subprocess.

Size

About 4 to 6 working days of agent time, done as five reviewable steps:

  1. Merge engine adapter and its tests
  2. Record format, reading and checking, and writing it on every apply
  3. Update core: rebuild, compare, merge per item, safe mode
  4. Commands, results, adopt, and the version A→B fixtures
  5. Specifications, schema, user guide, and example

It starts after the answers-file work (caller routes and identity) is merged, because update uses its answers check.

Complexity

high

  • First Toha data stored inside the project, and the first line merge.
  • Three ownership kinds times five situations each, plus safe mode.
  • Rebuilding an old version must reproduce the original answers exactly.

With this plan it stays manageable:

  • The deciding logic is one pure function, tested without files or processes.
  • The planner, injection, interview engine, and hooks are reused unchanged.
  • Every rule above has a named test that fails if the rule is removed.
