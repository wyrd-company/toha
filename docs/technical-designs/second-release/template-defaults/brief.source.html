Toha 0.2.0 · Design brief (revised) · Postplan

Template defaults via named stored values

Reuse an answer across templates by naming it and referencing it — never by pretending two questions mean the same thing because they share a field id.

task 1073 role: architect Phase C — awaiting Bob's approval reshaped: global-by-id removed paired impl 1058

Revised per Bob's canonical instruction. Consumes bundled-demo f949b6a. Prior global-by-id design superseded (history 37e2215).

Task

Design template-specific configured defaults for Toha 0.2.0 and obtain Bob's explicit approval of the exact revision before implementation 1058. This task produces a reviewed design package and this brief; it does not implement the feature.

The reshape. The earlier model — a config defaults map keyed by question id that implicitly overrode the matching question in every template — is rejected. A template author and a config author cannot assume two questions sharing an id (title, email, owner) mean the same thing. There must be no implicit application by id.

The new model. Config holds a named store of reusable values (called values, deliberately not defaults). A template-specific default explicitly references a stored value (by name) or an inline literal, for a named question of a selected template identity. A value reaches a question only because a mapping says so.

Pre-mortem — it failed. Why?

  • Implicit coupling crept back. A value applied to a question by id, coupling independent authors. Mitigation: nothing is applied by id; a value reaches a question only via an explicit mapping (B2).
  • Literal vs reference was ambiguous. A literal that spelled a value name was read as a reference. Mitigation: { value: name } is a reference; a bare scalar/array is a literal; the schema oneOf makes any other object a hard error, not a misread (B3, B7).
  • A dangling reference produced a silent empty default. Mitigation: a missing reference is a clear error naming the file, the mapping site, and the value (B4).
  • Cycles / unbounded resolution. Mitigation: references live only in mappings and resolve one hop into a literal store — cycles are impossible by construction (B7), no detector needed (D4).
  • Migration lost data. An existing defaults: block was silently dropped or silently reinterpreted. Mitigation: reject-with-conversion — data stays in the file, nothing runs until converted (D1, B13).
  • The engine drifted. Identity or the store leaked into the pure engine. Mitigation: resolution at the boundary; engine consumes the unchanged flat Seed.defaults (B12, B14).

Module and seam

Two files carry the feature (config.rs, interview.rs); the third change is four one-line call-site edits. Resolution stays in the toha library so every driver and crate path is served by one code path. The pipeline below Seed is unchanged.

   config files: values + template-defaults   (system, user, local .toha.yml)
        |  parse ONCE: classify leaf (reference vs literal), parse names/ids, tag file/layer
        v
   src/config.rs -- Config { values, template_defaults, .. }   [+2 fields, -defaults]
        v
   src/cli/resolve.rs -- ResolvedTemplate (UNCHANGED) -> formal_name (stable identity)
        v
   src/interview.rs -- configured_defaults(formal_name, template, values, mappings)
        |   pick mappings[formal_name]; for each id the template DEFINES:
        |     reference -> look up values   (missing -> attributed error)
        |     literal   -> use verbatim
        |     validate used value's kind vs question kind (attributed)
        |   -> IndexMap<Id, RawAnswer>      <- identity + store flattened away here
        v
   src/main.rs::seed / continue / apply / progress  ->  Seed { now, defaults }
        v
   PURE ENGINE, identity- and store-UNAWARE          [behavior UNCHANGED below Seed]

Config (values + mappings; defaults removed)

pub struct ValueName(String);   // ^[a-z_][a-z0-9_]*$ — NOT a question id

pub enum DefaultSource {
    Ref(ValueName),               // `{ value:  }` — resolve against `values`
    Literal(serde_json::Value),   // bare scalar or string array — verbatim
}

pub struct Config {
    pub templates_paths: Vec<PathBuf>,
    pub local_templates_paths: Vec<PathBuf>,

References appear only in mappings and resolve one hop into a literal store → cycles impossible by construction. Three disjoint key types (value name / formal identity / question id).

Proposed schema edit (applied by 1058)

$defs:
  value-name: { $ref: "#/$defs/identifier" }
  literal:
    oneOf: [ { type: string }, { type: boolean },
             { type: array, items: { type: string } } ]
  reference:
    type: object
    additionalProperties: false
    required: [value]
    properties: { value: { $ref: "#/$defs/value-name" } }
  default-source:
    oneOf: [ { $ref: "#/$defs/reference" }, { $ref: "#/$defs/literal" } ]

Reviewer focus

  • Any implicit id application? Find a path where a value reaches a question without an explicit mapping.
  • Literal/reference confusion? Find a literal read as a reference, or a reference read as a literal.
  • Silent failure? Find a missing reference or type mismatch that does not error, or errors without naming the config file/site.

Decisions needed first (Bob)

D1 — Migration of existing defaults: (required)

Reject-with-conversion (recommended): a defaults: block is a load error naming the file and showing the exact values: + template-defaults: rewrite. Data stays in the file; nothing runs until converted; no silent behavior change.

vs adopt-into-values-with-warning (data-preserving fallback if a real 0.1 install base is confirmed; values stop applying until mapped — a silent behavior change) vs deprecation-window (rejected — revives the removed coupling). Auto-translate is infeasible (no identity to translate into). removes global-by-id, as directed load-bearing, no silent data loss

D2 — Reference/literal representation

Concise (recommended): { value: name } reference + bare scalar/array literal, airtight via the schema oneOf.

vs distinct keys (value: / literal:): maximally explicit and greppable, future-proof against object answers, but every literal is wrapped. Both unambiguous.

D3 — Names

values for the store (all three candidates converged; not defaults) and template-defaults for the mappings, with { value: name } references. Alternatives: stored-values, library, constants. recommend values + template-defaults

D4 — Value chaining

Disallow value → value references (recommended): cycles impossible by construction, no escape rule needed. vs allow chaining with a cycle detector and a literal escape (more power, more surface). recommend disallow

D5 — Validation scope + reuse-kind limit (disclosure)

Validate when the template defines the question (recommended; consistent with today, deterministic, catches errors early) vs only when the question is reached given when/batch.

Disclosure (not a choice): a stored value has one answer kind (its JSON shape), so one value can seed only questions of that kind — documented, not a defect.

Risks and disclosures

  • D1 removes the global-by-id capability — this is the replacement Bob directed and authorized; the migration disposition is how it is removed without silent data loss. Deck inclusion is disclosure, not approval.
  • No permission/access change, timeout, pinned check, or application subprocess is introduced by any decision.
  • Reuse is bounded to one answer kind per stored value (D5) — a cross-judge-surfaced property, to be documented.
  • Migration naming trap — authors may name values after question ids and expect implicit application; a docs guardrail steers names away from ids, and reject-with-conversion forces explicit intent.
  • Cross-family judging unavailable this run; base pick rests on one family's scoring plus the orchestrator's independent read, which agreed exactly.
