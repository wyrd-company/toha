Toha 0.2.0 · Design brief (approved) · Postplan

Template defaults via named presets

Reuse an answer across templates by naming it as a preset and referencing it — never by pretending two questions mean the same thing because they share a field id.

task 1073 role: architect APPROVED by Bob — in independent review reshaped: global-by-id removed paired impl 1058

Approved with one naming delta: store = presets, reference = { preset: name }. Consumes bundled-demo f949b6a. Prior global-by-id design superseded (history 37e2215).

Task

Design template-specific configured defaults for Toha 0.2.0. Bob has approved this exact revision (with the naming delta below); it is handed to independent review and binds paired implementation 1058.

The reshape. The earlier model — a config defaults map keyed by question id that implicitly overrode the matching question in every template — is rejected. A template author and a config author cannot assume two questions sharing an id (title, email, owner) mean the same thing. There is no implicit application by id.

The model. Config holds a named store of reusable presets (called presets, deliberately not defaults). A template-specific default explicitly references a preset (by name) or is an inline literal, for a named question of a selected template identity. A preset reaches a question only because a mapping says so.

Pre-mortem — it failed. Why?

  • Implicit coupling crept back. A preset applied to a question by id, coupling independent authors. Mitigation: nothing is applied by id; a preset reaches a question only via an explicit mapping (B2).
  • Literal vs reference was ambiguous. A literal that spelled a preset name was read as a reference. Mitigation: { preset: name } is a reference; a bare scalar/array is a literal; the schema oneOf makes any other object a hard error, not a misread (B3, B7).
  • A dangling reference produced a silent empty default. Mitigation: a missing reference is a clear error naming the file, the mapping site, and the preset (B4).
  • Cycles / unbounded resolution. Mitigation: references live only in mappings and resolve one hop into a literal preset store — cycles impossible by construction (B7), no detector needed (D4).
  • Migration lost data. An existing defaults: block was silently dropped or reinterpreted. Mitigation: reject-with-conversion — data stays in the file, nothing runs until converted (D1, B13).
  • The engine drifted. Identity or the preset store leaked into the pure engine. Mitigation: resolution at the boundary; engine consumes the unchanged flat Seed.defaults (B12, B14).

Module and seam

Two files carry the feature (config.rs, interview.rs); the third change is four one-line call-site edits. Resolution stays in the toha library so every driver and crate path is served by one code path. The pipeline below Seed is unchanged.

   config files: presets + template-defaults   (system, user, local .toha.yml)
        |  parse ONCE: classify leaf (reference vs literal), parse names/ids, tag file/layer
        v
   src/config.rs -- Config { presets, template_defaults, .. }   [+2 fields, -defaults]
        v
   src/cli/resolve.rs -- ResolvedTemplate (UNCHANGED) -> formal_name (stable identity)
        v
   src/interview.rs -- configured_defaults(formal_name, template, presets, mappings)
        |   pick mappings[formal_name]; for each id the template DEFINES:
        |     reference -> look up presets   (missing -> attributed error)
        |     literal   -> use verbatim
        |     validate used value's kind vs question kind (attributed)
        |   -> Resolution { defaults, warnings } <- identity + presets flattened here
        v
   src/main.rs::seed / continue / apply / progress  ->  Seed { now, defaults }
        v
   PURE ENGINE, identity- and preset-UNAWARE          [behavior UNCHANGED below Seed]

Public interfaces expected

Resolver (in the toha library)

/// Project the preset store + per-identity mappings onto ONE selected template.
/// Replaces configured_defaults(template, &config.defaults).
/// Only questions the template DEFINES are considered; refs resolve against
/// `presets`; the used value's kind is checked against the question.
pub fn configured_defaults(
    formal_name: &str,
    template: &Template,
    presets: &IndexMap<PresetName, ConfigEntry<Value>>,
    mappings: &IndexMap<String, IndexMap<Id, ConfigEntry<DefaultSource>>>,
) -> Result<Resolution, EvalError>;

pub struct Resolution { pub defaults: IndexMap<Id, RawAnswer>, pub warnings: Vec<String> }

Attribution (graft: C2 file + C3 provenance)

pub struct EvalError {
    pub id: Id,
    pub field: &'static str,
    pub message: String,
    pub expression: Option<String>,
    pub config_key: Option<String>,   // NEW, e.g.
    //  <mapping-file>: template-defaults."gh:owner/collection".agree
    //  -> <preset-file>: presets."flag" ("yes-please")
}

Missing-reference and literal errors lead with the winning mapping file. A referenced type error also names the winning preset file after the provenance arrow. Unknown-question warnings name the winning mapping file/site.

Config (presets + mappings; defaults removed)

pub struct PresetName(String);   // ^[a-z_][a-z0-9_]*$ — NOT a question id

pub enum DefaultSource {
    Ref(PresetName),              // `{ preset:  }` — resolve against `presets`
    Literal(serde_json::Value),   // bare scalar or string array — verbatim
}

pub enum ConfigLayer { System, User, Local }
pub struct ConfigOrigin { pub layer: ConfigLayer, pub path: PathBuf }
pub struct ConfigEntry<T> { pub value: T, pub origin: ConfigOrigin }

pub struct Config {
    pub templates_paths: Vec<PathBuf>,
    pub local_templates_paths: Vec<PathBuf>,
    // REMOVED: pub defaults: IndexMap<Id, Value>
    pub presets: IndexMap<PresetName, ConfigEntry<Value>>,
    pub template_defaults:
        IndexMap<String, IndexMap<Id, ConfigEntry<DefaultSource>>>,
    pub hosts: IndexMap<String, String>,

Each per-key merge replaces value + exact path/layer together. References appear only in mappings and resolve one hop into a literal preset store → cycles impossible by construction.

Proposed schema edit (applied by 1058)

$defs:
  preset-name: { $ref: "#/$defs/identifier" }
  literal:
    oneOf: [ { type: string }, { type: boolean },
             { type: array, items: { type: string } } ]
  reference:
    type: object
    additionalProperties: false
    required: [preset]
    properties: { preset: { $ref: "#/$defs/preset-name" } }
  default-source:
    oneOf: [ { $ref: "#/$defs/reference" }, { $ref: "#/$defs/literal" } ]

Reviewer focus

  • Any implicit id application? Find a path where a preset reaches a question without an explicit mapping.
  • Literal/reference confusion? Find a literal read as a reference, or a reference read as a literal.
  • Silent failure? Find a missing reference or type mismatch that does not error, loses the winning mapping file, or loses referenced-preset provenance.
  • Engine purity & parity? Find identity/presets leaking past the boundary, or a driver/crate path that diverges.

Decisions — Bob-approved

D1 — Migration of existing defaults: = reject-with-conversion

A defaults: block is a load error naming the file and showing the exact presets: + template-defaults: rewrite. Data stays in the file; nothing runs until converted; no silent behavior change. Deprecation-window rejected; auto-translate infeasible. Adopt-into-presets-with-warning is the only fallback, and only if a real 0.1 defaults: install base is confirmed. removes global-by-id, as directed no silent data loss

D2 — Representation = concise

{ preset: name } reference + bare scalar/array literal, airtight via the schema oneOf. The distinct-key alternative was declined.

D3 — Names = presets / template-defaults

The store is presets (the approved revision of the arena's working name values); mappings are template-defaults; references are { preset: name }.

D4 — Chaining = disallow

No preset → preset references; cycles impossible by construction, no escape rule needed.

D5 — Validation scope = validate-when-defined

Validate a mapping when the template defines the question (consistent with today, deterministic, catches errors early). Disclosure: a preset has one answer kind (its JSON shape), so one preset can seed only questions of that kind — documented, not a defect.

Risks and disclosures

  • D1 removes the global-by-id capability — the replacement Bob directed and authorized; the migration disposition removes it without silent data loss.
  • No permission/access change, timeout, pinned check, or application subprocess is introduced by any decision.
  • Reuse is bounded to one answer kind per preset (D5) — a cross-judge-surfaced property, documented in the guides.
  • Migration naming trap — authors may name presets after question ids and expect implicit application; a docs guardrail steers names away from ids, and reject-with-conversion forces explicit intent.
  • Cross-family judging unavailable this run; base pick rests on one family's scoring plus the orchestrator's independent read, which agreed exactly.
