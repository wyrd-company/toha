Toha 0.2.0 · Design brief · Postplan

Template-specific configured defaults

Scope a default answer to a template identity, so two templates that both ask title can get different defaults — while global-by-id defaults stay unchanged and the pure interview engine learns nothing new.

task 1073 role: architect Phase C — awaiting Bob's approval paired impl 1058

Design revision: git 46b8acb · base epic/second-release bbebb35 · consumes bundled-demo f949b6a

Task

Design template-specific configured defaults for Toha 0.2.0 and obtain Bob's explicit approval of the exact design revision before the paired implementation (1058) starts. This task produces a reviewed design package and this brief; it does not implement the feature.

The problem. Toha's defaults config maps a question id to a value; that value replaces the matching question's default in every template that asks that id. Two templates that both ask title are forced to share one default. There is no way to say "for template X default title = A; for template Y default title = B."

The shape. Add an identity-scoped tier — template-defaults, keyed by a template's stable formal_name — that overlays the preserved global-by-id tier. All identity resolution happens at the config/resolve boundary and flattens into the same Seed.defaults: IndexMap<Id, RawAnswer> the engine already consumes.

Pre-mortem — it failed. Why?

  • Keyed on the wrong thing. Defaults keyed on a short name or an ambiguous selector let two templates collide, or made a config key raise the exit-5 ambiguity error. Mitigation: key on formal_name, matched by equality against the already-resolved identity — never re-resolved through the registry.
  • Precedence was not total. A question id matched by both a global and a scoped default, in different layers, resolved differently across runs. Mitigation: total (specificity, layer) order; only the winner is validated; same-layer/same-specificity ties are refused, not guessed.
  • The engine drifted. Identity leaked into the pure engine, so the driver paths diverged or resume froze stale defaults. Mitigation: resolver lives in a boundary module; engine gains only an extracted pure validator; defaults re-resolve on resume.
  • A supported capability was narrowed silently. Global-by-id was removed or reinterpreted without approval. Mitigation: global-by-id kept unchanged as the base tier (D3); any narrowing is flagged for explicit approval.
  • Defaults vanished on a version bump. A ref-pinned template lost its defaults when the ref changed. Surfaced as decision D4, not silently decided.

Module and seam

Three boundary files touched, one new module (src/cli/defaults.rs). The engine is untouched except for one extracted pure validator it already contained. Below resolve_defaults the flow is byte-for-byte the existing path.

/// Resolve the effective configured defaults for ONE resolved template.
/// Total & deterministic; only the WINNING value per id is validated; re-runnable
/// so all driver paths and resume agree.

    identity: &TemplateIdentity<'_>,

Decisions needed first (Bob)

D1 — Precedence primary axis

Specificity primary (recommended) vs layer primary.

A template-specific default beats a global one even from a higher layer — precision states intent. Consequence: a system scoped default beats a local global default. All three candidates recommend specificity primary; pinned by B5 either way. low-reversibility once shipped

D2 — Selector surface

Minimal (recommended): keys are the stable formal identity only — smallest vocabulary, zero new ambiguity, solves the stated problem.

vs qualified (formal:/alias:/name:/path:): richer — alias addressing and an intentional short-name broadcast — but wider vocabulary, with alias:/name: registry-relative. The base architecture makes qualified an additive later change. additive either way

D3 — Global-by-id disposition

Keep defaults unchanged as the base tier (recommended): purely additive, no narrowing, no approval needed.

vs deprecate/fold it away — removes a supported capability; requires explicit approval. Not recommended. This design proposes no supported-capability restriction.

D4 — What defines a default's identity key across versions

The key is the resolved formal_name. A ref-pinned git address (gh:a/b@v1 vs @v2) is a different key, so a ref bump silently drops its scoped defaults; an installed template updated in place keeps its key.

Recommend (i) ref-sensitive exact formal_name, documented (users key on the unpinned/installed formal name for stability) vs (ii) a ref-insensitive convenience key. Local path keys resolve relative to the config file, so committed .toha.yml stays portable. cross-judge-flagged risk

Risks and disclosures

  • No supported-capability restriction, permission/access change, timeout, pinned check, or application subprocess is introduced — provided D2 = minimal or qualified (both additive) and D3 = keep unchanged. Deck inclusion is disclosure, not approval.
  • D1 and D4 are the low-reversibility choices; both are put to Bob with a recommendation and a pinning test, not silently decided.
  • Cross-family judging unavailable this run; base pick rests on one family's scoring plus the orchestrator's independent read, which agreed exactly. Recorded limitation.
  • The global-by-id capability is preserved unless Bob separately approves a specific restriction.
