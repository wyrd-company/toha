Toha 0.2.0 · Design brief · task 1071

Trust management for installed templates

Grant and revoke hook-trust for a template you already installed — reading only the installed folder, never fetching or moving the commit — with two plain verbs.

architect · phase C awaiting approval consumes design 1069 paired impl 1054

Task

Design the command surface a caller uses to grant and revoke hook-trust for an already-installed template, consuming the approved 1069 trust policy without redefining it.

  • The gap today: after 1069, trust is entry.approval: Option<ReviewDigest>, granted for a fresh install by templates add --trust. There is no way to (re)approve an installed template — the only path, templates add --trust <formal>, re-clones and in fact refuses a bare installed name. The untrusted-hooks refusal points there anyway.
  • The fix: two verbs — templates trust <name> records the digest of the installed executable surface; templates untrust <name> clears it. No fetch, no reclone, no commit change. The refusal names the new operation.
  • This task produces the reviewed design and this brief; the paired task 1054 implements it.

Pre-mortem — the design and implementation failed. Why?

  • Trust fetched or moved the template. A grant re-cloned or rewrote commit, so "trust" silently changed what would run. Addressed: trust loads entry.path only and set_approval touches no field but approval; no arm reaches source:: or set_commit. Proved by a byte-identical commit/path test run offline.
  • The trust rule was re-implemented in the command (raw approval == digest), and a later edit diverged it from the gate. Addressed: idempotency routes through evaluate_trust; the command holds no equality. This is exactly the regression that sank a rejected candidate.
  • Blind approval: a caller trusted hooks they never saw. Addressed: the path to trust runs through the exit-3 refusal / apply --dry-run that list the hooks; the grant echoes the approved surface to stderr.
  • A system-only template gained a user approval, or the local layer granted trust. Addressed: resolve_user keys off the user file; local schema forbids approval. A system/local-only name is refused not-in-user-registry.
  • Scriptability broke — a new interactive gate a CI run could not pass. Addressed: both verbs are non-interactive; stdout stays the result line; the surface echo is advisory on stderr.

Module and seam

No new module. Two command functions in src/cli/templates.rs and one new immutable mutator in src/registry.rs, over the 1069 library. The interview engine gains nothing.

Public interfaces expected

Two clap subcommands (new arms)

/// Approve the installed hooks of a template so its apply runs them.
Trust   { template: String },   // formal, short, or alias name
/// Revoke approval of a template's hooks.
Untrust { template: String },
// No options, no groups, no runtime exclusivity check.
// A missing operand is clap's own exit 2.

Command functions (crate seam via run())

fn trust(ctx: &Context, name: &str) -> Result<Vec<String>, CommandError>;
fn untrust(ctx: &Context, name: &str) -> Result<Vec<String>, CommandError>;
// trust:   resolve_user → Template::load(entry.path) → HookSurface::of
//          → evaluate_trust (idempotency) → set_approval(Some(digest)) → stderr echo
// untrust: resolve_user → set_approval(None)   [no HookSurface call]

Registry mutator (new; single writer of the field)

impl RegistryFile {
    /// Copy with `formal`'s approval set (Some) or cleared (None), marking
    /// FieldPresence for the sparse round-trip. Errs if `formal` is absent.
    /// Touches no other field — source/ref/commit/path/aliases unchanged.
    pub fn set_approval(&self, formal: &str, approval: Option<ReviewDigest>)
        -> Result<RegistryFile, RegistryError>;
}

ReviewDigest, HookSurface, evaluate_trust, Entry.approval are the 1069 types, consumed unchanged.

Idempotency is defined through evaluate_trust: a surface changed since approval is not "already trusted" — trust re-records and reports trusted.

Behaviors to prove (falsifiable)

Central behaviors

  • Grant records the installed surface, no fetch. trust writes approval == HookSurface::of(installed).digest(); commit/path/source byte-identical; succeeds offline.
  • Revoke clears and reads nothing. untrust omits the approval key and succeeds even with an absent/unreadable folder.
  • Idempotency through the chokepoint. Second trust on an unchanged surface → already trusted, no write; after a change → re-records, trusted.
  • Update → lapse → re-trust. A surface-changing update lapses effective trust (next apply exits 3); trust re-approves with no fetch; a doc-only update keeps trust.
  • Refusal names the new op in every adapter; ambiguous name re-offers templates trust <each> (exit 5).
  • Layer boundary. System/local/discovered/unknown name → not-in-user-registry (exit 1), no write.

Out of scope

  • The trust policy and the digest / evaluate_trust / HookSurface library — owned by 1069 / 1033; consumed here.
  • The apply gate, exit-3 contract, and dry-run listing — unchanged.
  • A dedicated read-only templates review verb — the hook listing is already apply --dry-run and the exit-3 refusal.
  • The --digest <sha> freshness pin and diff-since-approval display — recorded as future extensions (Decision B).
  • Trusting a system-only template from the user side — every mutating templates command is user-registry only; unchanged.

Reviewer focus — what the adversarial reviewer will attack

  • Does any path re-implement the trust equality outside evaluate_trust (the raw-== regression that sank Candidate 1)?
  • Does set_approval touch any field but approval, or does any path reach source:: / set_commit, so a grant could move or re-fetch the template?
  • Is the not-in-user-registry boundary keyed off the user file, not the merged registry, so a system-only template cannot silently gain a user approval?
  • Does the refusal name templates trust in every adapter (interactive, dry-run, ambiguous retry), and does the sparse round-trip truly omit a cleared approval (never approval: null)?

Decisions needed first

Decision 1 — command shape product decision

  • A. Verb pair templates trust + templates untrust — recommended. Flagless, legible; less clap machinery than a toggle for a one-operand inverse pair; makes the trust-reads / untrust-reads-nothing asymmetry visible; clean refusal breadcrumb. Scored highest on fidelity, scriptability, legibility.
  • B. Dual-mode templates trust <name> / --remove (the task's first-listed option). Rejected: degenerate mirror of alias; awkward --remove.
  • C. templates review <name> [--approve|--revoke]. Rejected: overloads a read name; duplicates apply --dry-run.

Decision 2 — scriptable freshness pin --digest <sha>

  • A. Defer — recommended. Baseline stays the clean verb pair; the atomic read→digest→write already closes the review→approve window, and evaluate_trust re-checks at apply. Adding --digest later is backward-compatible.
  • B. Include now, with a distinct exit code for drift.

Decision 3 — refusal wording (Question 3)

The untrusted-hooks refusal names templates trust <formal> in place of templates add --trust, with the hooks listed above it. Resolves Question 3 as "yes, name the new operation." Question 2 is settled by 1069 (approval binds the surface digest, not the commit) and is not reopened.

Permissions / access — disclosed separately needs explicit approval

  • Permissions/access: these commands grant and revoke the permission to run a template's hooks (write/clear entry.approval in the user registry) — a new operator surface for a security-relevant permission. It grants no permission the operator lacked (add --trust / apply --trust already do); it adds a no-fetch way to manage it and a revoke where none cleanly existed.
  • Filesystem read scope: trust reads the installed template's executed-file bytes via HookSurface::of — within entry.path only; no write beyond the user registry, no network.
  • No capability removed, no new timeout, no pinned-version check, no application-subprocess integration.

Complexity

Low, with this plan. No new module, no new domain type, no gate or engine change; the design reuses the established resolve_user → immutable-RegistryFile → single-user-write path that alias/remove/update already follow.

  • Dependency: 1054 depends on 1033 for src/review.rs and entry.approval; the design (this task) does not.
  • Main risk is discipline, not difficulty: keep the equality solely in evaluate_trust and set_approval touching only approval — both covered by named sole-kills.
