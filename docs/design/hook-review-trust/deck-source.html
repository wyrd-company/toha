Toha 0.2.0 · Design brief · task 1069

Hook-script review & trust persistence

Bind hook approval to reviewed executable content, so a template update that changes the code that runs can no longer keep stale trust.

architect · phase C awaiting approval paired impl 1033

Task

Design hook-script review and trust persistence so a caller can review the executable hook content before a trusted install and before an update keeps trust, and so an update that changes the executable input drops trust until it is reviewed again.

  • The hole today: trust is a whole-template trusted: bool bound to the template name. templates update re-clones to a new commit and never touches trusted, so a changed script: body or run: line runs on the next apply with no review and no --trust.
  • The fix: approval binds to a digest of the executable surface; effective trust is always the live compare of the approved digest to the freshly computed one — nothing to carry, drop, or sync.
  • This task produces the reviewed design and this brief; it does not implement the feature.

Pre-mortem — the design and implementation failed. Why?

  • Under-invalidation: the digest missed a changed file, so trust survived a code change — e.g. a run: [python, scripts/x.py] whose script bytes were never hashed. Addressed by Decision 2 (hash literal in-tree run/args paths); residual gap for Jinja-substituted paths is disclosed.
  • Over-invalidation: trust broke on every commit or doc-only change, users learned to blanket --trust, and review became noise. Addressed: digest covers only hook nodes + executed-file bytes; docs/questions/files excluded.
  • Silent field escape: design 1078 added a hook field that the digest did not cover, so new executable syntax escaped review. Addressed: digest hashes the whole parsed node value, not a serde-derive; a field-coverage guard test fails if any field stops changing the digest.
  • Trust logic leaked across registry/apply/cli, and a later edit re-introduced the stale-trust bug. Addressed: one evaluate_trust chokepoint; no settable bool; apply path never writes approval.
  • An adapter broke or UI leaked into the interview engine. Addressed: engine stays answer→question; review is a pure library value; HookRunner stays the only port; exit-3 contract unchanged.

Module and seam

One new pure module, src/review.rs. The apply gate reduces to one boolean decided by the chokepoint. apply.rs and HookRunner are unchanged.

                approval digest (stored)            executable-surface digest (live)
 templates.yml ──────────► registry.rs ──► resolve.rs (ResolvedTemplate.approval)
                                                   │
 template.yml ─load(+!include)─► template.rs ─► review.rs  HookSurface::of / digest / diff
   (parsed hook nodes)               │                     (pure, UI-free)
                                     ▼
     main.rs apply gate: trusted = --trust || evaluate_trust(approval, live) == Trusted
                                     │      (the ONE trust chokepoint; list & update call it too)
                                     ▼
                          apply.rs  (bool in → NeedsTrust out; UNCHANGED)
                                     ▼
                          HookRunner (the one library port; UNCHANGED)

Interview engine gains nothing: no review/prompt port, no trust or digest knowledge, no UI.

Public interfaces expected

Review surface (new, pure)

// src/review.rs — pure; no I/O beyond reading executed-file bytes
impl HookSurface {
    pub fn of(template: &Template) -> Result<Self, ReviewError>;
    pub fn digest(&self) -> ReviewDigest;              // deterministic, answer-independent
    pub fn diff(&self, prior: &HookSurface) -> HookSurfaceDiff;
}

The trust chokepoint (only producer of "trusted")

pub enum Trust { Trusted, NeedsReview }

pub fn evaluate_trust(
    approved: Option<&ReviewDigest>,
    live: &ReviewDigest,
) -> Trust;  // Trusted iff approved == Some(live)

Equality is the whole policy. The stale-trust state is unrepresentable.

Apply gate (binary), replacing the bool seam

let live = HookSurface::of(&template)?.digest();
let trusted = trust  // --trust one-run flag
    || matches!(evaluate_trust(resolved.approval.as_ref(), &live), Trust::Trusted);
plan.apply_reporting(path, ApplyOptions { force, trusted }, &ProcessRunner, &mut on_written)?;

Data structures expected

Registry entry (replaces the bool)

pub struct Entry { /* name, source, ref, commit, path, aliases (unchanged) */
    pub approval: Option<ReviewDigest>,   // was: pub trusted: bool
}
pub struct ReviewDigest(String);          // "sha256:<64 hex>", constructor-guarded

FieldPresence.trusted → .approval; sparse round-trip and layer-merge precedence carry over. add inherit becomes approval.or(old.approval) — safe, since an inherited digest grants trust only while live content still matches.

The reviewable surface

struct HookView {
    origin:  HookOrigin,        // Interview{index} | TopLevel{index}
    node:    CanonicalNode,     // sorted-key encoding of the PARSED node value (not serde-derive)
    scripts: Vec<ScriptDigest>, // sha256 of every executed in-tree file
}

What counts as changed executable input

  • Each hook node's canonical encoding — all fields (run/script/args/cwd/when/each and any future field), in surface order.
  • The bytes of every executed in-tree file: every declared script: target, and (Decision 2) every literal in-tree run:/args path.
  • Everything else — generated files, questions, messages, docs — is excluded.

Behaviors to prove

Invalidation matrix (the central falsifiable test)

Change since approvalExpected apply outcome
no changehooks run
doc-only changehooks run (approval stands)
hook-line changeneeds review — exit 3, listed as changed
script-byte changeneeds review — exit 3, listed as changed

Other proofs

  • Update keeps/drops trust: doc-only update → next apply runs; hook/script update → next apply exits 3 and lists the change.
  • Field-coverage guard: adding a field to a hook node changes the digest; a test fails if it does not.
  • Answer-independence: different answers over one template → same digest.
  • Adapter parity: headless --answers, staged resume across processes, and crate callers all reach the same gate.

Sole-kill (for the implementer)

  • Force evaluate_trust to always return Trusted → invalidation-matrix tests fail.
  • Drop script bytes from the digest → script-byte-change test fails.
  • Digest a serde-derive instead of the parsed value → field-coverage guard fails.

Out of scope

  • Trust-management command syntax (review / approve / untrust / list-trust) — owned by design 1071. This design exposes the library operation and names the plug-in point only.
  • The opt-in Jinja hook-result fields themselves — design 1078. This design only guarantees they are covered automatically.
  • Multi-revision / rollback approval (a set of approved digests) — recorded as a future extension; the single-digest field can grow into a set without breaking callers.
  • Canonical spec/schema edits are described, not applied — the paired implementation (1033) makes them in the same change.

Reviewer focus

The adversarial reviewer will be told to attack:

  • Escapes from the digest: any way a hook can run code whose bytes are not in the digest — Jinja-substituted script paths, run args that resolve to files, symlinks out of the template root, !included hook nodes.
  • Answer-dependence: can any answer set change what the digest covers, or activate a dormant hook that was not reviewed?
  • Determinism: is the canonical encoding stable across serializer versions and map ordering, so an approved digest does not spuriously drift?
  • Leakage / drift: is evaluate_trust truly the only producer of "trusted", and does the apply path ever write approval?
  • Adapter regressions: exit-3 contract, dry-run listing, staged resume, local-layer-never-trusts.

Decisions needed first

  • 1. Capability narrowing (needs approval). Trust no longer survives an executable-surface change on update. Recommend approve — it is the defect this task closes; doc-only updates still keep trust.
  • 2. run-arg file coverage + read scope (permissions/access). Also hash literal in-tree run/args paths; accept a residual gap for Jinja-substituted paths. Reads bytes within the template root only — no write, network, or out-of-root access. Recommend approve option A.
  • 3. Future bundled template that ships hooks. Today's bundled demo ships no hooks (confirmed with 1074). Recommend defer — nothing here blocks either later choice.
  • 4. Legacy trusted: true migration. Pre-v1, no users. Recommend re-approve on next apply (no migration step); a legacy bool reads as needs-review — the safe direction.

Deck inclusion alone does not grant approval; the capability-narrowing and permissions/access items above are called out separately and require explicit sign-off.

Size

  • S–M for the paired implementation (1033).
  • One new pure module (~200–300 lines with tests), a one-field registry-entry change with round-trip, a one-line apply-gate swap, the update re-evaluation, and the described spec/schema edits.
  • Most of the effort is tests: the invalidation matrix, field-coverage guard, answer-independence, and adapter parity.

Complexity

  • moderate with this plan. The risk concentrates in one place — the canonical encoding and exactly which bytes the digest covers — and the plan pins both.
  • Low integration risk: apply.rs, HookRunner, the exit-code contract, and every adapter are unchanged; the gate still consumes one bool.
  • The single evaluate_trust chokepoint keeps the trust rule in one testable function, so the stale-trust class of bug is designed out rather than guarded against.
